The Hexagon backend, for people who have never touched a DSP

nntrainer can run a small language model (Qwen3-0.6B) on the signal processor (Hexagon cDSP) inside a Snapdragon 8 Elite phone instead of on the phone's CPU. This guide explains how that works, how to run it, and how to read the numbers. Everything here is taken from docs/backend_guide/HEXAGON.md, HEXAGON_BENCHMARK.md, the code under nntrainer/tensor/hexagon/ and Applications/CausalLM/hexagon/, and docs/measurements/23-sdk64-baseline.md; each number says where it came from.

The one-paragraph mental model

The phone's main processor (the host, an arm64 Android CPU) does three things. First, once at start-up, it converts the model's weights into one big byte image in a memory area both processors can see, and hands that image, an empty key/value cache and a scratch buffer to the DSP together with a short recipe called the op-list (HEXAGON.md §1, §1.1). From then on the DSP owns the whole graph: it keeps the buffers mapped for the life of the session and knows every step of the model. Second, for each chunk of prompt tokens or each generated token, the host sends only the token ids and the position, and the DSP runs the entire recipe in one remote call (one FastRPC round-trip, about 0.26 ms; HEXAGON.md intro, §8 M1 test 231 / 255 / 284 µs min / median / max). Third, the host reads back the logits (one score per vocabulary word, 151,936 floats for this model; HEXAGON.md intro) and picks the next token. There is no per-layer chatter between the two processors, which is the whole point of the design.

Three facts to hold on to

  • Toolchain. Every build happens in the dev container with Hexagon SDK 6.4 (6.4.0.2 in the container; the workstation that built the 2026-09-17 device binaries has 6.4.0.1) and hexagon-clang 19.0.04 (HEXAGON.md §5.2; tools/docker/README.md; 23-sdk64-baseline.md "Artifacts").
  • Wire contract. Host and DSP agree on op-list ABI version 4 (NNTR_HTP_ABI_VERSION in nntr_htp_common.h); init() rejects any other version before touching memory (HEXAGON.md §1).
  • v75 is the gate, v79 is faster. The shipping skel is built with HEX_ARCH=v75 and runs unchanged on v79 silicon. A v79-native build is 10–27 % faster on the same phone with matching accuracy, but four simulator tests fail by ±1 LSB on v79, so a v79 change must pass both the simulator and the device before the default flips (HEXAGON.md §7 rule 1, §5.2, §9).
