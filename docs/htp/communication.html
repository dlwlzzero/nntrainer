How the CPU and the NPU talk

The NPU runs one thing in this backend: the MoE feed-forward block. Everything else stays on the ARM CPU. So every token crosses the CPU–NPU boundary 22 times, once per MoE layer. Each crossing carries a few kilobytes of activation; the ≈ 22 MB of expert weights per call never cross, the DSP reads them from shared memory. Terms are defined at the bottom of the page.

1. The actors, on one picture #

Three places run code and three memories hold data. The ARM process and the DSP never share a thread; they share memory, ION buffers in DDR that both sides map. The FastRPC driver in the kernel routes each call.

memoryholdswritten → readlives for
ION arena (DDR, uncached on the CPU)all expert weights, ≈ 3.6 GiBARM once at load → DSP every callthe session
staging buffers (DDR, cached ION)one call's activation and outputARM ↔ DSP, every callreused per size class

The arena is uncached on the CPU, so the one-time writes reach DDR without a flush and no call ever pays cache work on it. The staging buffers are cached but small, and sized to the call: the driver flushes a whole buffer per call, so decode's 8 KB activation rides a 64 KiB buffer, never a prefill-sized one.

2. Life of a session #

A process opens one FastRPC session and keeps it until exit. Everything expensive happens once, before the first token; after that a decode token is 22 plain calls.

  • Open: load our DSP code without signing (unsigned PD), ask the driver to poll for replies instead of sleeping, take all of VTCM, lock the HMX, start 5 worker threads, vote DSP clocks and bus bandwidth up.
  • Load: write each expert matrix into the ION arena in the NPU tile layout (Weight format), register it with the DSP by pointer, and free the ARM copy.
  • Warm-up: one prefill-sized call, so the first real call pays no first-time costs. It also sends the option word once and checks that the DSP echoes it back.

3. Life of one MoE call (decode) #

One decode token makes 22 of these calls. Step through the diagram, or read the list below it.

  1. Router (CPU). Lfm2MoELayer picks 4 of the 32 experts for the token.
  2. Hand off. The routing is flattened into arrays and passed to HtpComputeOps.
  3. Prepare. Look up each expert's DSP weight handle, take the call lock, copy the 8 KB activation into a 64 KiB staging buffer.
  4. Stub call. The generated stub packs the arguments. The clock for host starts.
  5. Driver. Maps the staging buffers into the DSP (no copy), flushes them, signals the DSP.
  6. Skel (DSP). Unpacks the arguments, copies the activation in, starts the kernel. The clock for dsp starts.
  7. Kernel. Quantize the activation, run gate/up and down for each expert from VTCM (section 4b), sum the four outputs. The matmuls are 677 of the 712 µs.
  8. Return. Copy the output to the staging buffer; the skel returns.
  9. Reply. The driver flushes the output buffer and posts the reply.
  10. Poll sees it. The ARM thread has been spinning, so it sees the reply at once, with no interrupt wake-up.
  11. Copy out. Copy the output into the layer's tensor and release the lock.
  12. Back in the layer. The CPU continues to the next layer.

3.1 Where the time goes #

The DSP times its own stages; the ARM times the whole stub call. The difference, host − dsp, is everything the boundary costs.

transport = host − dsp82.2186.7

The transport used to be 401 µs per call. Size-class staging buffers and the polling wait cut it to 88 µs; the VTCM feed then shortened it further.

4. Three ways weights reach the compute units #

The activation is kilobytes; the weights are 22 MB per call. So the layer's speed is decided by how the weights get from the arena to the unit that multiplies them. HMX reads only VTCM, and VTCM holds 8 MiB, so each path is a choice of who moves the bytes and through which memory.

Two measured facts decide between b and c: the DMA engine moves 31–37 GB/s depending on the phone, while HVX loads from DDR stop near 23.5 GB/s; and HVX reading VTCM while the DMA writes into it costs almost nothing (0.1–0.3 %).

4a. Prefill: the DMA ring into VTCM, HMX tiles #

HMX multiplies only operands in VTCM, so prefill stages everything through a ring of chained DMA descriptors. The first expert's weights start moving before the activation is even quantized; HMX then works through 64-row blocks while worker threads run the epilogues one block behind, and the next expert's weights stream into the buffer the previous one just freed. Details: HMX matmul, MoE FFN §3.

4b. Decode default: the VTCM feed #

At one token every weight byte is used once, so decode is a stream. The DMA engine copies whole expert matrices into two VTCM slabs, one expert ahead, and HVX computes from the copy. Each matrix is one DMA descriptor; as soon as HVX finishes with a slab, the next matrix is queued into it, so the engine never idles.

The call now runs at the DMA engine's rate (32.6 GB/s in the call), so the MoE floor is simply bytes ÷ engine rate: 13.0–15.5 ms per token depending on the phone. Against the arena read, the feed is +25.7 % decode.

4c. The previous path: the arena read #

Still the fallback when the slabs do not fit. Each of the 6 HVX lanes loads its slice of the weights straight from the arena through L2, and prefetches the next block 192 KB ahead with l2fetch so loads do not wait on DDR.

It lost because HVX loads from DDR top out around 23.5 GB/s, while the DMA engine delivers 31–37 GB/s.

5. Synchronization rules #

Nothing runs concurrently across the boundary: the ARM thread blocks for the whole call, and on the DSP one caller thread drives everything else.

rulewhat it guarantees
One call at a time, under one lock.The staging buffers, VTCM and the HMX lock have one owner.
Poll, don't sleep, for up to 5 ms.A call returns without an interrupt wake-up. Without it, decode is 11 % slower.
Fork/join per stage on the 6 HVX lanes.A join is a full barrier: every lane's reads and writes are done.
DMA descriptors finish in order.Waiting on one means every earlier copy has landed.
A slab is refilled only after its join.The DMA never overwrites bytes a lane is still reading. A host test checks the schedule.
The arena needs no flush: uncached, written once at load.The DSP always reads what the ARM wrote, with no per-call cache work.
Option echo on the first call.An out-of-date DSP binary fails loudly instead of silently running another path.

Terms #

NPU / DSP / HTP
The same device: the Hexagon processor on the SoC. The code says htp; its compute DSP is the cDSP.
HVX
Hexagon Vector eXtensions: the DSP's 1024-bit SIMD units. The worker pool uses 6 of them. Good at one-row (matrix × vector) work.
HMX
Hexagon Matrix eXtensions: the matrix-multiply unit. It always computes 64-row tiles and reads only VTCM.
VTCM
8 MiB of fast on-chip memory next to HVX/HMX. The session takes all of it when it opens.
DMA
The DSP's user DMA engine. It copies DDR ↔ VTCM on its own while HVX/HMX compute. It is driven by a ring of chained 2D descriptors.
FastRPC
Qualcomm's remote procedure call from an ARM process to the DSP. One call blocks the calling ARM thread until the DSP returns.
stub / skel
Two pieces that the qaic tool generates from test/htp/nntr_hvx.idl. The ARM-side stub packs the arguments; the DSP-side skel (libnntr_hvx_skel.so) unpacks them and runs our code.
PD
Protection domain: the DSP process our skel runs in. Ours is an unsigned PD, so no code signing is needed.
ION / rpcmem
ION is Android's shareable DMA-buffer memory. rpcmem_alloc allocates it, and an fd names it, so both the ARM and the DSP can map the same pages.
l2fetch
A DSP instruction that asks the L2 cache to prefetch a 2D box of memory in the background.
