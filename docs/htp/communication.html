How the CPU and the NPU talk

The NPU runs one thing in this backend: the MoE feed-forward block. Everything else in LFM2.5-8B-A1B stays on the ARM CPU. So every token crosses the CPU–NPU boundary 22 times, once per MoE layer. Each crossing carries the few kilobytes of a token's activation, while the DSP reads about 22 MB of expert weights that never cross. This page draws that boundary: who the actors are, how a session is set up, what happens in one call, and the three ways the weights travel from DDR to the compute units.

Snapshot htp_moe @ a7c66dec, default path: the VTCM feed. Measured numbers come from the Galaxy S25 Ultra (Snapdragon 8 Elite, Hexagon v79). Each carries its source: a sitting number from docs/htp_moe/BENCHMARK.md or a rule in LEDGER.md. Results: the results page.

Terms used on this page
NPU / DSP / HTP
The same device: the Hexagon processor on the SoC. The code says htp; its compute DSP is the cDSP.
HVX
Hexagon Vector eXtensions: the DSP's 1024-bit SIMD units. The worker pool uses 6 of them. Good at one-row (matrix × vector) work.
HMX
Hexagon Matrix eXtensions: the matrix-multiply unit. It always computes 64-row tiles and reads only VTCM.
VTCM
8 MiB of fast on-chip memory next to HVX/HMX. The session takes all of it when it opens.
DMA
The DSP's user DMA engine. It copies DDR ↔ VTCM on its own while HVX/HMX compute. It is driven by a ring of chained 2D descriptors.
FastRPC
Qualcomm's remote procedure call from an ARM process to the DSP. One call blocks the calling ARM thread until the DSP returns.
stub / skel
Two pieces that the qaic tool generates from test/htp/nntr_hvx.idl. The ARM-side stub packs the arguments; the DSP-side skel (libnntr_hvx_skel.so) unpacks them and runs our code.
PD
Protection domain: the DSP process our skel runs in. Ours is an unsigned PD, so no code signing is needed.
ION / rpcmem
ION is Android's shareable DMA-buffer memory. rpcmem_alloc allocates it, and an fd names it, so both the ARM and the DSP can map the same pages.
l2fetch
A DSP instruction that asks the L2 cache to prefetch a 2D box of memory in the background.

1. The actors, on one picture #

Three places run code and three memories hold data. The ARM process and the DSP never share a thread. They share memory: two kinds of ION buffers in DDR that both sides map. The FastRPC driver in the kernel routes each call between them.

The two ION kinds differ on purpose. The arena is written once and never read by the CPU. Its CPU mapping is uncached, so the writes reach DDR with no flush, and the driver never has to maintain it. The staging buffers are cached and small, and they are reused on every call. The driver's cache maintenance covers the whole buffer, so each buffer is sized to the call: decode's 8 KB activation rides a 64 KiB buffer, never a prefill-sized one (StagingPool, PR #103).

2. Life of a session #

A process opens one FastRPC session. It holds the DSP's resources (VTCM, the HMX lock, the worker threads) until the process exits. Everything expensive happens once, before the first token: mapping ≈ 3.6 GiB of expert weights (22 layers × 32 experts × 5.25 MiB), taking VTCM, starting threads, voting clocks. After that, a decode token is 22 plain calls.

What each phase buys

  • Unsigned PD. remote_session_control(DSPRPC_CONTROL_UNSIGNED_MODULE) lets the skel load without code signing.
  • Latency control. remote_handle64_control(DSPRPC_CONTROL_LATENCY) asks for RPC_POLL_QOS with a 5000 µs window (NNTR_HTP_POLL_US changes it). If the driver refuses, it falls back to RPC_PM_QOS at 100 µs. Section 5 shows what polling saves.
  • DSP open. nntr_hvx_open allocates the session struct and takes the whole VTCM. It locks the HMX for the session, starts hvx_worker_pool_create(n_hvx − 1) (5 worker threads on v79, and the calling thread is the sixth lane) and places HAP_power votes. The votes are apptype COMPUTE, DCVS v2 performance mode with 100 µs wake latency and NOM–TURBO corners, and a 40 GB/s bus request.
  • Load, per chunk. ensureArena / tryChunk allocate an uncached ION chunk of at most 256 MiB, halved when a request is refused. fastrpc_mmap with FASTRPC_MAP_FD maps it into the PD. With flag 0 (FASTRPC_MAP_STATIC) the DSP-side HAP_mmap_get refuses the mapping. Then nntr_hvx_arena_attach records {fd, va, bytes} in one of 32 arena slots.
  • Load, per weight. The matrix is written into the chunk in the WH tile layout (32 × 32 int4 tiles of 512 B; see weight format). nntr_hvx_weight_register_u8i4_arena(K, N, arena, wh_off, w_scale, colsum_w, bias) returns a uint32 slot in the 2048-entry weight table. releaseArmSource then gives the ARM copy's pages back with madvise(MADV_DONTNEED), unless NNTR_HTP_KEEP_ARM_WEIGHTS is set.
  • Options once. The first MoE call (the warm-up) runs sendMoeOptsOnce, which sends the option word with moe_set_opts and checks the echo (section 5). With nothing set, the startup banner reads applied=0x303e1 … feed=vtcm.

3. Life of one MoE call (decode) #

One decode token makes 22 of these calls. Each one starts from the router output in Lfm2MoELayer and returns the MoE block's output for that token. Step through the diagram, or read the numbered list below it. The list is the whole story, and the buttons only highlight one step at a time.

  1. Router, on the CPU. Lfm2MoELayer computes the router logits (the FP32 gate plus expert_bias) with dot(). Then buildExpertAssignments picks 4 of the 32 experts for the token.
  2. Flatten and hand off. tryMoeLayerOnAccelerator flattens the routing into three arrays: row_index, row_count (one entry per expert, 32) and row_weight. It then calls ops->gemm_qs4cx_moe_layer_fp32. ops is HtpComputeOps, which the layer's context got from HtpContext.
  3. Prepare the call (ARM). Every expert's gate_up and down matrix gets a DSP weight handle (get_or_register_wh); after load, each one is a hit in handle_cache_. sendMoeOptsOnce does nothing after the first call. The thread then takes invoke_mutex_ and picks the staging buffers by size class (stage(act_pool_, …)). The 1 × 2048 FP32 activation (8 KB) lands in the 64 KiB buffer, copied by stagedMemcpy. This copy happens before the timer starts, so it is not part of host.
  4. Stub call. nntr_hvx_mm_u8i4_moe_layer, the qaic-generated stub, packs the scalars into a 48-byte primitive block. The five small arrays (32 + 32 handles and the routing) go as plain heap sequences. The activation and output go as pointers into the ION staging buffers. The ARM wall clock around this call is the profile's host time.
  5. Driver. The FastRPC driver sees that the staging buffers are ION, so it maps them into the DSP's PD rather than copying them. It does cache maintenance over each whole buffer, then signals the DSP. The whole-buffer maintenance is why the staging pools use size classes: when one buffer was sized for prefill, every 8 KB decode call paid for a multi-MB flush.
  6. Skel on the DSP. The skel unpacks the arguments. The kernel copies the activation from the FastRPC buffer into its heap scratch with one DMA descriptor. Then hexkl_mm_u8i4_moe_layer_run starts. It gets the session's weight table, VTCM, worker pool, scratch and option flags. From here until the reply is the profile's dsp time.
  7. The kernel. quant (7.7 µs) quantizes and packs the activation. Stage A computes gate/up with the fused SwiGLU, one pool run per expert. It reads the expert's weights from a VTCM slab that the DMA engine filled; section 4b shows how. requant (9.4 µs) requantizes each expert's intermediate. Stage C computes the down matrix, again one pool run per expert, and scatter (7.5 µs) adds the four outputs, each times its router weight. Stages A and C with their slab waits are mm: 677.2 of the 711.7 µs.
  8. Return. A second DMA descriptor copies the 1 × 2048 output into the FastRPC output buffer (stage, 5.7 µs for both copies). The skel returns.
  9. Reply. The driver finishes the call: it does cache maintenance on the output buffer and posts the reply.
  10. Poll sees it. HtpBackend set a poll-QoS window of 5000 µs, so the ARM thread has been spinning since step 4 rather than sleeping. It sees the reply at once and does not pay an interrupt wake-up. host − dsp = 82.2 µs is the whole round-trip overhead (the transport).
  11. Copy out, unlock. stagedMemcpy copies the output from the staging buffer into the layer's tensor. The mutex is released when invokeMoeLayer returns.
  12. Back in the layer. Lfm2MoELayer has the MoE FFN output for the token and continues on the CPU. The same round trip repeats for each of the 22 MoE layers of every token.

3.1 Where the time goes #

The level-2 profile (NNTR_HTP_PROFILE=2) calls the _timed variant of the entry. The DSP returns its own stage timers, and the ARM measures the wall clock around the stub call. host − dsp is everything the boundary costs: stub, driver, cache maintenance and wake-up. The transport was not always this small. Before PR #103, the staging used one buffer sized for the largest call, and the driver flushed all of it on every call. The poll window was also 100 µs. Measured in sitting #88, the size-class pools and the 5 ms poll together cut the M == 1 transport from 401.3 to 87.9 µs per call (LEDGER ⑦). Putting only the poll back to 100 µs (#88 C) cost 11.0 % of decode at G = 64 against B. The feed then halved the transport again, from 186.7 to 82.2 µs in the table above. LEDGER rule 35 records that effect: the direct HVX arena read made the call boundary slower, and the cause is not yet separated.

4. Three ways weights reach the compute units #

The activation is kilobytes; the weights are megabytes. Four experts at top-4 read 21 504 KB per decode call, 22.02 MB in all (#117 B's ring line). The layer's speed is therefore decided by one question: how do those bytes get from the ION arena to the unit that multiplies them? The backend has three answers. HMX can read only VTCM, and VTCM holds 8 MiB, so every path is a choice of who moves the bytes and through which memory.

Two measured facts decide between b and c. The DMA engine alone moves 31–37 GB/s, depending on the unit (the anchor cell, LEDGER rule 34). HVX reading VTCM while a DMA writes into it costs only 0.1–0.3 % (LEDGER rule 29). So letting the engine stage the weights and HVX read the copy is faster than HVX pulling from DDR itself. The layouts below show how each path uses VTCM, on one scale.

4a. Prefill: the DMA ring into VTCM, HMX tiles #

HMX multiplies only operands that sit in VTCM, so prefill must stage everything. The caller thread owns the ring (hexkl_dma_ring.c): 256 hexkl_dma_desc2d slots, chained with dmlink onto the in-flight descriptor and started once with dmstart. Each push is a 2D transfer (push2d(dst, src, dst_stride, src_stride, row_size, nrows)).

  • The first expert's gate_up goes out before the quantization scan, as paired gate/up chunk lists (at most 16 chunks per list; 4 for gate_up and 2 for down at this model's shape). The scan runs while it is in flight.
  • The pool's background lane packs the activation into 64-row blocks (submit_bg). Each block is pushed into VTCM's activation slot behind the weights.
  • For each 64-row block and chunk: hexkl_dma_ring_wait on that chunk's index, then hexkl_micro_hmx_mm_u8i4, then hmx_acc_read_int32. Pool workers run the dequant + SwiGLU, requant, down, dequant and scatter epilogues one job behind the HMX.
  • Buffer A is reused with a time offset. Once expert e's last gate_up matmul is done, expert e+1's gate_up is pulled into A while e's down runs from B.

A prefill call at prompt 512 measures dsp 16 986.0 µs, of which mm is 10 222.0 µs, plus 1978.5 µs of transport (#120 A, M>1 row). The HMX path's deeper story is in the HMX matmul chapter and MoE FFN §3.

4b. Decode default: the VTCM feed #

At M = 1 there is nothing to amortize: every weight byte is used once. The feed (PR #118, the default since d79c0efe) turns the call into a stream. The DMA engine copies whole expert matrices into two VTCM slabs, one expert ahead, and HVX computes from the copy.

  • Slabs. G0 sits at offset 0 and G1 at gu_bytes (3.5 MiB). Expert i's gate_up goes into slab i & 1 (moe_m1_gu_off). Once a slab has no gate_up left to hold, it takes two downs (moe_m1_dn_off: slab (j >> 1) & 1, half j & 1).
  • One descriptor per matrix. moe_m1_push issues each matrix as one 2D descriptor (row = n_col × 512 B, k_tiles rows). At top-4 that is 8 weight descriptors per call, plus the activation copy-in and output copy-out: the ring reads desc=10/call.
  • Order. gate_up e0 → G0 and e1 → G1 go out before the quantization scan. After stage A of expert i joins, gate_up i+2 goes into the slab that i just freed. After the last two gate_ups, the downs follow.
  • No prefetch under the feed. The l2fetch lead is forced off (m1.lead_kb = 0). An l2fetch of a VTCM address means nothing, and one of the arena would pull the same bytes twice.

What was measured. #117 B's ring line reads engine 32.3..34.4 GB/s and busy=640..681 µs of a 711–712 µs dsp, with first 3584 KB took 110 us = 33.2 GB/s. #120 A's ring line again reads engine 32.3..34.4 GB/s. Over the whole call, 22.02 MB go through VTCM at 32.6 GB/s (BENCHMARK, cycle-15 budget). The ≈ 240 µs of HVX compute hides under the transfer, as LEDGER rule 29 predicted. In other words, the call now runs at the DMA engine's rate, and the MoE floor is bytes ÷ engine rate: 13.0–15.5 ms per token, depending on the unit (LEDGER rule 34). Against the arena read, the feed is +25.7 % decode at G = 64 (#120 A 35.97 vs A0 28.62 tok/s).

4c. The arena read with an l2fetch lead (FEED=0) #

This was the decode default from PR #115 until the feed landed. It is still the fallback when the slabs do not fit, and it runs when NNTR_MOE_HTP_GEMV_FEED=0 is set. No engine is involved: each of the 6 lanes takes a contiguous, expert-major slice of the 512-byte weight tiles and loads them straight from the arena through L2. So that loads do not wait on DDR, a lane issues an l2fetch box for block b+1 before it computes block b. The lead is 192 KB (HVX_GEMV_PF_LEAD_KB, NNTR_MOE_HTP_GEMV_LEAD_KB), with the one-row loop (ROWS1=1). The hardware queues three l2fetch boxes per thread and stalls the thread on a fourth, so the code keeps at most three outstanding.

Why it lost: HVX vector loads from DDR top out at 21–27 GB/s on this SoC (≈ 23.5 with the one-row loop and 192 KB lead). The engine delivers 31–37 GB/s (LEDGER rules 32 and 34). The difference is the whole +25.7 % above.

5. Synchronization rules #

Nothing in this backend runs concurrently across the boundary. The ARM thread blocks for the whole call, and inside the DSP one thread (the caller) drives everything else. The picture below shows one call at the moment the feed is running. The table lists every rule and where the code enforces it.
