LFM2.5-8B-A1B on the Hexagon NPU — results

LFM2.5-8B-A1B is an 8B-parameter mixture-of-experts (MoE) language model. We run it with nntrainer on a Galaxy S25 Ultra (Snapdragon 8 Elite, Hexagon v79). In the measured setup, the MoE feed-forward layers (22 per token) run on the Hexagon NPU (Qualcomm's DSP-based accelerator; "NPU" and "DSP" name the same processor on these pages). Everything else (attention, convolutions, norms, the router, lm_head) runs on the ARM CPU. This page shows how fast that setup is today.

In short: the NPU path prefills about 1.56× faster than the CPU. It decodes at about 0.73× the CPU's speed and 1.39× short of the goal. Even with every avoidable cost removed, the byte floor of today's split (the CPU and the NPU reading their weights one after the other) is about 42–47 tok/s. So 50 tok/s is not reachable by bytes alone without changing how the two read memory.

NPU vs CPU#

Two parts of the chip do the work:

  • HVX (Hexagon Vector eXtensions): the NPU's wide SIMD vector unit.
  • HMX (Hexagon Matrix eXtensions): its matrix-multiply unit.

Prefill processes the 512-token prompt at once. The MoE layers then run as large matrix multiplies on HMX, which is where the NPU is strong. Decode produces one token at a time. Each token has to read the weights of the 4 active experts in all 22 MoE layers from DRAM, so decode speed is set by bytes per second, not by arithmetic. On the NPU path, decode also pays one CPU↔NPU call per MoE layer, and the CPU's own work between the calls.

Phones of the same model differ. Across the two phones, and across days on one phone, NPU decode tok/s drifts by up to about 16 %. The NPU DMA engine reads 31–37 GB/s depending on the unit. That is why the project only reads a speed-up as a verdict inside one sitting (measurement.html §1.2). The CPU and NPU rows above come from different sittings, and none of the NPU sittings since #94 ran a CPU cell.

Distance to the goal#

The goal is ≥ 50 tok/s decode at every generation length. The NPU path is at 35.96 tok/s at gen 512, which is 1.39× short. At gen 64 it is also 1.39× short, and at gen 1024 it is 1.42× short.

What the floor says. A byte floor is the time needed just to read a token's weights at the memory's measured speed, with no other overhead.

  • MoE floor: 13.0–15.5 ms. Each decode token reads 22.02 MB of expert weights per MoE layer, 484 MB in all. The NPU pulls them from DRAM with its DMA engine (the hardware copy engine that moves data without the cores). That engine reads 37.3 GB/s on one phone and 31.2 GB/s on the other, so this part alone costs 13.0–15.5 ms.
  • CPU floor: ≈ 8.2 ms. The CPU reads the other 408 MB per token: conv projections, lm_head, dense FFN, attention projections and routers. It reads them at ≈ 50 GB/s, the rate the CPU-only model reaches.
  • Together: ≈ 21–24 ms per token (21.2–23.7), or ≈ 42–47 tok/s. The two reads happen one after the other, because the CPU waits for each MoE call.

So 50 tok/s (20 ms) is not reachable with today's serial CPU→NPU split by bytes alone. Even the fastest phone's floor, 21.2 ms, is above 20 ms. Getting there needs one of three things (roadmap.html):

  • the CPU and the DSP reading at the same time;
  • fewer bytes per token;
  • a faster DSP read.

BENCHMARK.md's cycle-16 budget still uses ≈ 6.5 ms for the CPU part (≈ 246 MB at 38 GB/s). Counting from the tensor shapes gives 408 MB, see lessons.html D1.

Where a decode token's time goes#

At gen 512 the NPU path makes one token every 27.81 ms (1000 / 35.96). The level-2 profile of the same sitting splits one MoE call into two parts. Multiplying each by the 22 MoE calls per token gives this split:

  • MoE work on the NPU (DSP time): 22 × 0.712 ms = 15.7 ms. Of that, the expert matmuls take 14.9 ms.
  • Transport: 22 × 0.082 ms = 1.8 ms. This is the cost of the CPU↔NPU round trips. Each call is a FastRPC call, Qualcomm's remote-procedure-call mechanism by which ARM code invokes a function on the DSP.
  • Everything outside the call: the token time minus the rest, ≈ 10.3 ms (37 %). This is the CPU's FC, attention, conv, norm and lm_head work between calls.

Read against the floor:

  • The MoE part (15.7 ms) has at most ≈ 2.7 ms left on the faster phone, and almost nothing on the slower one.
  • Round trips and CPU work take 1.8 + 10.3 = 12.1 ms. Against the CPU's ≈ 8.2 ms byte floor, that leaves ≈ 3.9 ms to win.
  • Even with both parts at their floors the token takes 21.2–23.7 ms, so the last step to 20 ms has to change the bytes or how they are read (roadmap.html).

By generation length#

Decode speed holds nearly flat from gen 64 to gen 1024 on the NPU path (35.97 → 35.17). The CPU slows more (52.43 → 48.31). The CPU clears 50 tok/s at gen 64, but not reliably at gen 512 or gen 1024.

Accuracy#

The NPU model is not bit-for-bit the CPU model:

  • CPU model (q40): every weight is in Q4_0.
  • NPU model (q40-qs4cx-wh): the MoE expert weights are in QS4CX_WH, a 4-bit layout packed for the NPU kernels (weight-format.html). The rest is Q4_0, as in the CPU model.

Different expert weights give slightly different logits, so "same text as the CPU" is not a meaningful test for the NPU path. Instead each change is checked two ways:

  • Text identical to its own control. The generated text of every variant is byte-compared with variant A of the same sitting, which is the previous default on the same NPU model. The [HTP] banner and md5 lines are excluded from the comparison.
    • The VTCM feed (PR #118): 36/36 runs identical over #117's two sittings. Then 2/2 at gen 64 in #120, where the pre-feed path (A0) ran against the new default.
    • The prefetch lead (PR #115): 6/6 in #113.
    • The transport fix (PR #103): identical to A in all of #88's B runs.
    • The HVX decode path: identical to the HMX path in #94's C runs.
    • Repeated runs of the default give the same text (run 1 = run 2 at every gen in #120 A).
  • Bit-identical kernels. The device test MoeLayerM1GemvMatchesHmx compares the decode (HVX GEMV) path with the HMX path on the phone. With the VTCM feed on and off, in both #117 sittings, it reports bit_identical yes, 0 bad elements of 40 960 (M = 1) and 0 of 163 840 (M = 4).

Progress#

Each merged decode change raised NPU decode at gen 512. The changes are:

  • Transport fix: ION shared-buffer staging and a longer FastRPC poll. ION is Android's shared-memory allocator that the CPU and DSP both map.
  • HVX GEMV: a vector-unit decode path in place of the matrix unit.
  • Prefetch lead: a 192 KB l2fetch lead in a one-row loop.
  • VTCM feed: the expert weights are DMA'd into VTCM one expert ahead. VTCM is the NPU's on-chip tightly-coupled memory, about 8 MiB of fast scratch that HVX and HMX read directly.

The full story of each change will be on the Optimizations page (in progress).
