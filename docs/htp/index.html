LFM2.5-8B-A1B on the Hexagon NPU

nntrainer runs LFM2.5-8B-A1B, an 8B-parameter mixture-of-experts (MoE) language model, on a Galaxy S25 Ultra (Snapdragon 8 Elite, Hexagon v79). The MoE layers run on the Hexagon NPU, everything else on the ARM CPU. The goal is ≥ 50 tok/s decode. This page is the whole project on one screen; each section links to the page with the detail.

1. The system#

  • Who runs what. The NPU (Qualcomm's DSP-based accelerator; "NPU" and "DSP" name the same processor here) runs only the MoE feed-forward, the part with most of the weights. Its two compute units are HVX, a wide SIMD vector unit, and HMX, a matrix-multiply engine.
  • How they talk. Each MoE layer is one FastRPC call (Qualcomm's mechanism for ARM code to call a function on the DSP). Only a few kilobytes of activation cross; the weights stay in shared memory. Communication
  • How the code is built. C++ classes in the app, a generated interface, C kernels on the DSP. Software

2. Where it stands#

Prefill handles the whole 512-token prompt at once as large matrix multiplies on HMX, where the NPU is strong. Decode makes one token at a time and reads every active weight once per token, so its speed is set by memory bandwidth, not arithmetic. That is why the NPU wins prefill and still trails the CPU in decode.

3. Where a decode token's time goes#

One decode token takes 27.8 ms; the goal needs 20 ms. 15.7 ms is the NPU reading expert weights, 1.8 ms is the 22 CPU–NPU calls, and ≈ 10.3 ms is CPU work between the calls.

The MoE part is within ≈ 2.7 ms of its floor and the CPU side has ≈ 4 ms left. Because the two read memory one after the other, even both floors add up to 21–24 ms, above 20 ms. The last step to 50 tok/s is a design change, not tuning.

4. How we got here#

Decode went from 18.3 to 36.0 tok/s in four merged changes: faster CPU–NPU calls, a vector-unit decode path, weight prefetch, and a DMA feed that copies each expert into on-chip VTCM memory one expert ahead. Optimizations has each change with its bottleneck and same-day gain.

5. What is next#

  1. One call per token. The per-token entry is in the tree behind a switch, and single-token NPU kernels for attention, norms and the conv gate have landed but are not wired in yet. Wiring them targets the 12.1 ms of calls and CPU work.
  2. The DMA engine's gap. Inside a call the engine reads 32–34 GB/s against 37 GB/s alone, worth up to ≈ 1.9 ms.
  3. Past the floor. 50 tok/s needs the CPU and the NPU reading memory at the same time, or fewer bytes per token.

6. Accuracy#

The NPU model stores its expert weights in a 4-bit layout packed for the NPU (Weight format), so its output is not bit-for-bit the CPU model's. Every change is checked two ways instead: it must produce exactly the same text as the code it replaces in every run, and an on-device test must show the decode and prefill paths compute identical numbers.
