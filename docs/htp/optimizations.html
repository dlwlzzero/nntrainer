How decode got from 18 to 36 tok/s

The upstream port put the MoE layers on the NPU and made prefill fast; decode started at 18 tok/s. Five measured changes since then took decode to 36 tok/s with identical output; a sixth has landed but is not measured yet. This page walks through them in order, each as bottleneck → change → measured gain.

1. The upstream port: one call per MoE layer#

Bottleneck

The first NPU version made two FastRPC calls (ARM → DSP remote calls) per expert: 176 calls per token. At ≈ 326 µs per call, that is ≈ 57 ms of transport per token before any compute.

Change

One call per MoE layer does the routing, all four experts and the weighted sum on the DSP. The expert weights are packed offline into the NPU's tile layout and copied once into a shared ION arena (Android memory that both the CPU and the DSP map), so no call carries weights. Inside the call, a pipeline streams weights into VTCM (the NPU's fast on-chip memory) while HMX (the matrix unit) computes.

2. Faster CPU–NPU calls#

Bottleneck

A decode call carries only 8 KB, yet its round trip cost 401 µs. The one staging buffer was sized for prefill, and the driver flushes the whole buffer on every call. The ARM thread also went to sleep 100 µs into the wait, and waking it cost more.

Change

Staging buffers come in power-of-two size classes, so decode uses a 64 KiB buffer. The ARM thread polls for the reply for up to 5 ms instead of sleeping.

Gain

Generated text identical to the control in every run. The poll alone matters: putting it back to 100 µs cost 11 % of decode.

3. Vector-unit decode#

Bottleneck

HMX computes 64-row tiles. A decode call has one token, so 63 of the 64 rows were padding: the matrix unit did 64 rows of work for one.

Change

Calls with up to 4 tokens skip HMX and run a matrix-vector product on HVX (the NPU's SIMD vector unit), split across 6 lanes. The result is bit-identical to the HMX path.

4. Weight prefetch and a one-row loop#

Bottleneck

On HVX, each weight load waited on DDR latency: the vector loop spent its time stalled, not computing.

Change

Each lane issues an l2fetch (a background prefetch into the L2 cache) 192 KB ahead of what it computes, and the inner loop takes one row of tiles per step instead of four.

Gain

5. VTCM feed#

Bottleneck

HVX loads from DDR top out near 23.5 GB/s. The NPU's DMA engine (its hardware copy engine) moves 31–37 GB/s, but decode did not use it.

Change

The DMA engine copies each expert's whole matrix into one of two VTCM slabs, one expert ahead, and HVX computes from the copy. The ≈ 240 µs of compute hides under the transfers, so a call now runs at the engine's rate.

6. Upstream sync#

Bottleneck

The upstream port kept improving after we forked it, mostly in prefill. In a prefill MoE call the down matmul waited for gate_up, and the requantize and dequantize steps between the matmuls cost ≈ 1.1 ms and ≈ 0.9 ms.

Change

We merged the latest upstream. Its prefill runs the down matmul one block behind gate_up and spreads the epilogue over the worker pool: requantize 1099 → 70 µs, dequantize 929 → 275 µs. Decode is unchanged.

7. Per-token entry (landed, not yet measured)#

Bottleneck

After the feed, a token still spends ≈ 1.8 ms in 22 round trips and ≈ 10.3 ms of CPU work between them. Neither shrinks one call at a time.

Change

A single forward call runs a validated op table on the DSP. Today the table's only DSP kernel is the MoE; the attention and small-op kernels have landed but are not wired in yet. The path is off by default, behind NNTR_HTP_FORWARD=1.

Gain

Not measured yet: it changes nothing until more ops run on the DSP.
