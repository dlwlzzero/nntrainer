1. The big picture #

Three layers: C++ classes in the app, a generated interface in the middle, and C modules in the DSP library. The model never talks to the DSP directly; it calls a ComputeOps interface, and the HTP engine swaps in HtpComputeOps.

  • ARM: the model picks the "htp" engine per MoE layer. HtpContext hands that layer HtpComputeOps, or the plain CPU ops if the DSP cannot be opened.
  • Boundary: one IDL file; qaic turns it into a stub linked into the app and a skel linked into the DSP library. They must be built from the same IDL.
  • DSP: one session struct holds everything that lives across calls: VTCM, the weight table, the worker threads. The MoE kernel is a single entry, hexkl_mm_u8i4_moe_layer_run, that picks the prefill or decode path by the number of rows.

3. The IDL #

test/htp/nntr_hvx.idl declares 52 methods. They fall into six families:

familywhat it doesexamplemethods
Weights and arenamap ION arena chunks into the DSP; register a weight matrix and get a handle backweight_register_u8i4_arena8
Matmul (FC)one quantized linear layer, fused gate/up + SwiGLU, the conv blockmm_u8i4_layer13
MoEone whole MoE layer per call, and the option word sent oncemm_u8i4_moe_layer3
Attention and small opsthe prefill-era attention and element-wise kernelsattn_forward10
Per-token entry off by defaultsend the op table once, then one call per token; the M=1 kernels it will wire inforward11
Probes and debugDMA bandwidth probes, trace readout, memory probesdma_probe7

Most matmul and attention methods come in pairs: x and x_timed. The _timed twin also returns the DSP's own stage timers; it is what NNTR_HTP_PROFILE=2 calls. open and close come from remote_handle64 and are not counted.

5. Switches #

The ones a reader needs; the rest are debug knobs.

switchdefaultwhat it does
moe_engine (model config)cpuhtp puts the MoE layers on the NPU
moe_htp_layers (model config)allwhich MoE layers go to the NPU
NNTR_HTP_PROFILEoff1–3: per-call timing, then the DSP's own stage timers
NNTR_MOE_HTP_GEMV_FEED10 falls back to the arena read for decode
NNTR_MOE_HTP_M1_GEMV10 sends decode through the prefill (HMX) path
NNTR_HTP_POLL_US5000how long the ARM thread polls for a reply
NNTR_HTP_FORWARDoff1 routes decode through the per-token entry (§6)

With nothing set, the startup banner prints the applied option word, applied=0x303e1 … feed=vtcm. If the DSP echoes back a different word, the app stops and says to rebuild the skel.

6. In the tree but not on the default path #

  • The per-token entry behind NNTR_HTP_FORWARD. Instead of 22 calls per token, the app sends a table describing the whole decode step once (graph_init), then makes one forward call per token. Today only the MoE op is filled in the DSP's kernel table, so it still makes one call per MoE layer. Off by default.
  • M=1 kernels landed, not wired. HVX versions of RMSNorm, RoPE, the conv gate and single-token attention with its KV cache are in the DSP library and pass their host checks, but the op table does not call them yet. Wiring them in is the next step toward one call per token (Roadmap).

Terms #

NPU / DSP / HTP
The same Hexagon processor. The code says htp.
HVX
Hexagon Vector eXtensions: the DSP's wide SIMD units; the backend uses 6 lanes.
HMX
Hexagon Matrix eXtensions: the matrix-multiply unit. It reads only VTCM.
VTCM
About 8 MiB of fast on-chip memory next to HVX and HMX.
FastRPC
Qualcomm's remote procedure call from an ARM process to the DSP.
IDL, stub, skel
The interface file, and the two halves qaic generates from it: the ARM-side stub packs arguments, the DSP-side skel unpacks them and calls our code.
ION
Android's shareable memory. Both the ARM and the DSP can map the same ION buffer.
M=1
One row of activation: one token, i.e. decode.
GEMV
Matrix × vector: the decode-time matmul.
