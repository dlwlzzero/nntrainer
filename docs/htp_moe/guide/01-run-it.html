1. Run it — from a clean clone to a decoded token on the phone

.claude/skills/hexagon-gates/SKILL.md (exact workstation commands), tools/htp/env.sh, docs/measurements/77-first-handoff.md "Steps" (install and run lines as they were actually executed), contract §4.1 and §11, Applications/CausalLM/{build_android.sh,install_android.sh}, LEDGER.md rules 1–6.

Two machines are involved. Everything is built on the Ubuntu workstation; the phone (a Galaxy S25 Ultra, Hexagon v79) only receives files over adb and runs them. Agents never touch the phone; the user does, from a written handoff. contract §4.1–4.2

1. Host build (no phone, no SDK; minutes)

The host build compiles nntrainer for the workstation itself. It gives you the quantizer (nntr_quantize_stream) that produces the phone's weight files, plus the unit tests that gate every change.

meson setup build -Denable-transformer=true -Denable-tflite-backbone=false \
  -Denable-tflite-interpreter=false \
  -Dc_args=-Wno-error=missing-include-dirs -Dcpp_args=-Wno-error=missing-include-dirs
ninja -C build

# the host gates ("rung 1")
./build/test/unittest/unittest_nntrainer_cpu_backend --gtest_filter='*qs4cx*'
NNTR_QUANTIZE_BIN=$PWD/build/Applications/CausalLM/nntr_quantize \
NNTR_QUANTIZE_STREAM_BIN=$PWD/build/Applications/CausalLM/nntr_quantize_stream \
  ./build/Applications/CausalLM/unittest_causallm_models --gtest_filter='*Lfm2Moe*'   # 6 PASSED, none skipped
bash test/htp/host/run_host_checks.sh     # prints ALL CHECKS PASS and WORKER POOL LANES OK
bash tools/htp_syntax_check.sh

run_host_checks.sh compiles the DSP kernel sources (hexkl_mm_u8i4_moe.c, the worker pool) on the workstation against scalar stand-ins of the HVX/HMX primitives and checks the kernel's loop structure and bit-identity to a reference. There is no Hexagon simulator in this project; this host check and the phone are the only two places a kernel is proven. hexagon-gates §1; contract §4.1

2. The DSP library ("skel"; seconds)

./test/htp/build.sh                      # v79, -Wall -Werror
md5sum test/htp/build/libnntr_hvx_skel.so   # record it; every handoff quotes it

libnntr_hvx_skel.so is the code that runs on the DSP. build.sh first runs qaic on test/htp/nntr_hvx.idl — the interface file that lists every remote function (mm_u8i4_moe_layer, arena_attach, …) — which generates a stub (ARM side, calls into the DSP) and a skel (DSP side, receives the call), then compiles the kernels under nntrainer/tensor/htp_backend/{hmx,hvx}/ and test/htp/*.c into the skel. hexagon-gates §2; test/htp/build.sh

Trap. build_android.sh never rebuilds the skel. Whenever the IDL or any DSP source changes, run test/htp/build.sh again and push the new skel. A stale skel fails on the phone with AEE_EBADPARM (0x8000040E). LEDGER rule 3

3. The Android app (≈ 10 min from scratch)

(cd Applications/CausalLM && ./build_android.sh --htp)       # --cache reuses builddir; --profile = a separate, never-for-tok/s build
readelf -d builddir/android_build_result/lib/arm64-v8a/libnntrainer.so | grep -E 'libsdkl|libcdsprpc'   # both NEEDED lines must appear
md5sum Applications/CausalLM/jni/libs/arm64-v8a/{nntrainer_causallm,libcausallm_core.so} \
       Applications/CausalLM/jni/obj/local/arm64-v8a/{libnntrainer.so,libccapi-nntrainer.so}
  • --htp passes -Denable-htp=true to meson and needs HEXAGON_SDK_ROOT. Without it the app has no DSP path at all. build_android.sh lines 20–30, 148, 200
  • Trap. --clean drops -Denable-htp silently; the readelf line is how you notice (libsdkl.so missing). LEDGER rule 4
  • With NDK r30 the shared libraries libnntrainer.so, libccapi-nntrainer.so, libc++_shared.so stay in jni/obj/local/arm64-v8a/, while install_android.sh looks in jni/libs/arm64-v8a/ first and copies from obj/local only when the file is missing there. Push the obj/local ones (or delete the stale copies in libs/) so the phone never gets an old build. hexagon-gates §3; install_android.sh "DEP_FILES" block
  • First build on a fresh workstation: tools/package_android.sh ends in ninja install and googletest tries to install to /usr/local; run cd builddir && meson configure -Dprefix=$PWD/android_build_result && ninja install once, then build_android.sh --htp --cache. The tokenizer library needs Rust once (build_tokenizer_android.sh). hexagon-gates §3 "Workstation specifics"

4. The two model files

Both are made from the same FP32 conversion of the Hugging Face checkpoint; they differ only in how the 32 × 22 expert matrices are quantized. contract §11; BENCHMARK.md "Artifacts"

directory under $NNTR_MODEL_DIRrolehow it is madefile, size, md5
hf/sourcehf download LiquidAI/LFM2.5-8B-A1B (bf16 safetensors, 17.0 GB, 2 shards)—
fp32/intermediateApplications/CausalLM/res/lfm2_moe/lfm2-8b-a1b/weight_converter.py --model_path hf/nntr_lfm2_8b_a1b_fp32.bin ≈ 31 GB
q40/CPU control — everything 4-bit Q4_0, the format the CPU kernels readnntr_quantize_stream fp32/ -o q40/ --fc_dtype Q4_0 --embd_dtype Q4_0 --lmhead_dtype Q4_0 --isa ARMnntr_lfm2_8b_a1b_q40_arm.bin, 4 768 855 808 B, d28f55c5bd7adeb8bf73b02de582eb88
q40-qs4cx-wh/NPU model — FC/embedding/lm_head Q4_0, experts QS4CX_WH (per-channel int4, bytes already in the HMX tile order)same plus --moe_dtype QS4CX_WH; its nntr_config.json gets "moe_engine": "htp", "moe_htp_layers": ""nntr_lfm2_8b_a1b_q40_arm.bin, 4 316 133 120 B, 7b7867fab51845664c0050c0a837073e
  • Always --isa ARM: the _arm.bin suffix must be present; an x86 packing runs silently wrong on the phone. contract §11
  • QS4CX_WH has no CPU fallback: the CPU cannot multiply by those bytes (FloatTensor::dot implements no path for them, on purpose). moe_htp_layers must be empty (= all MoE layers on the HTP). A wrong layout gives plausible wrong text, not an error. LEDGER rule 6; lfm2_moe_layer.cpp:486–504
  • The two models produce different text for the same prompt (different expert quantization), so "text identical to CPU" is checked within a model between runs, and across the two only when the same weights are used on both paths. 77-first-handoff.md §A; doc 49 §1

5. nntr_config.json switches

The app reads one JSON file per model directory. The keys that matter for decode on the NPU: the #78 output files at $NNTR_MODEL_DIR/{q40,q40-qs4cx-wh}/nntr_config.json; lfm2_moe_causallm.cpp:51–53; lfm2_causallm.cpp:337–348

keyvaluesmeaning
moe_engine"cpu" (default) / "htp"Which engine runs the MoE expert FFN. The WH model must say htp.
moe_htp_layers"" (= all) or a comma list of layer idsWhich MoE layers go to the HTP. Must be empty for QS4CX_WH.
moe_layer_dtypeQ4_0 / QS4CX_WHWritten by the quantizer; must match the weight file.
conv_in_proj_engine, conv_out_proj_engine, attn_proj_engine, dense_ffn_engine and their *_htp_layers"cpu" (default) / "htp"The same switch for the non-MoE matrices (doc 50 line of work). Neither #78 model file sets them, so in every measurement so far these run on the CPU.
init_seq_len512Prompt length the run is configured for (prompt fixed at 512 tokens in this project).
num_to_generate64 / 512 / 1024Generation length; the handoff edits it per run with sed.
bad_word_ids[124900] in the handoffBlocks one token id so the generation runs to the exact count.
tokenizer_filedevice pathPoints at tokenizer.json on the phone.

Also in generation_config.json: "do_sample": false (greedy decoding, so two runs of one model must produce identical text). 77-first-handoff.md step 1 "Config edits"

6. Install on the phone

# binaries and libraries (no models, no skel, no libsdkl.so)
(cd Applications/CausalLM && ./install_android.sh)      # → /data/local/tmp/nntrainer/causallm/

# the DSP library and the HexKL runtime, by hand
D=/data/local/tmp/nntrainer/causallm
adb push test/htp/build/libnntr_hvx_skel.so $D/
adb push $HEXKL_ROOT/lib/$HEXKL_SDK_VER/armv8_android26/libsdkl.so $D/

# the models (≈ 10 min: 4.7 GB + 4.3 GB)
M=/local/mnt/workspace/models/lfm2.5-8b-a1b
adb push $M/q40          $D/models/q40
adb push $M/q40-qs4cx-wh $D/models/q40-qs4cx-wh
adb push $M/hf/generation_config.json $D/models/q40/   # only if a model dir lacks it (the app throws without it)
Never push libcdsprpc.so from the build tree. It is a link-time stub; the phone's own /vendor/lib64/libcdsprpc.so is the real FastRPC driver, and shadowing it makes HtpBackend::enabled() false or silently corrupts results. LEDGER rule 5; mobile_e2e_run_guide.md §5

Note: install_android.sh in this tree takes no arguments and pushes only nntrainer_causallm, nntr_quantize, nntr_safetensors_info, libcausallm_core.so, libnntrainer.so, libccapi-nntrainer.so, libc++_shared.so (the mobile guide's --model= option does not exist here). The run_causallm.sh it drops on the phone sets NNTR_NUM_THREADS=4 and no ADSP_LIBRARY_PATH, so do not use it for measurements — use the explicit command below. install_android.sh lines 60–212

7. Run one decode

adb shell "cd /data/local/tmp/nntrainer/causallm && \
  NNTR_NUM_THREADS=8 LD_LIBRARY_PATH=. ADSP_LIBRARY_PATH=. \
  ./nntrainer_causallm ./models/q40-qs4cx-wh \"\$(cat prompt512.txt)\""
  • ADSP_LIBRARY_PATH=. tells the FastRPC driver where to find libnntr_hvx_skel.so for the DSP. LD_LIBRARY_PATH=. finds libsdkl.so and the nntrainer libraries.
  • NNTR_NUM_THREADS=8 for both CPU and NPU runs — every number in this project is measured that way. contract §1.1
  • prompt512.txt is a text that tokenizes to exactly 512 tokens (docs/measurements/77-prompt512.txt on branch htp/77-first-handoff, md5 fc65c158…). Run the CPU model first: its decode rate is the thermal gate (CPU decode < 30 tok/s means the phone is throttling — cool down and redo). 77-first-handoff.md step 2

Reading the output

After the generated text the app prints a fixed block (from Applications/CausalLM/models/causal_lm.cpp:699–710):

=================[ LLM with NNTrainer ]===================
prefill: 512 tokens, 1054 ms, 485.769 TPS
generation: 512 tokens, 27861 ms, 18.3756 TPS
total: 28915 ms
peak memory: 5323824 KB
==========================================================
  • prefill: — tokens in the prompt, the time to process them, and tokens per second. The count must read 512; anything else means a tokenizer mismatch and voids the prefill column.
  • generation: — tokens generated, wall time, and decode tok/s over the whole generation. This is the number the goal is read against. The count must equal num_to_generate.
  • A generation(last 64): line (decode tok/s over the last 64 tokens, contract §1.1) is planned but is not printed by this model yet: Lfm2MoeCausalLM reports from the base block in causal_lm.cpp, not from lfm2_causallm.cpp's block where the line was added (issue #89, LEDGER rule 16).
  • Example values above are #77 A, q40-qs4cx-wh, G=512 run 1, unit R3CY205ZMND. 77-first-handoff.md §A

Instrumentation switches (environment variables)

variablewhat you getsource
NNTR_HTP_PROFILE=1Host-side timing of the three stages a weight goes through (conversion, registration, the per-call layer call).htp_compute_ops.cpp:175–181
NNTR_HTP_PROFILE=2Also routes every layer call through the _timed IDL entry, so the DSP reports its own microseconds per stage and transport = host − dsp becomes a measurement. Printed at exit as a [HTP-PROFILE] table with one row per shape (M==1 = decode, M>1 = prefill) and a weight DMA: line with the in-call GB/s.same; 77-first-handoff.md §B pasted lines
NNTR_HTP_PROFILE=3Same, but each call is repeated 5× on the same input and the fastest is kept — removes DDR/temperature noise from the DSP columns. Output text is unchanged. Caveat: it inflates [M0-PROF] ffn= ~5×; only the [HTP-PROFILE] host/dsp/transport columns are comparable across levels 2 and 3.htp_compute_ops.cpp:1479–1490; LEDGER rule 15
NNTR_M0_PROFILE=1ARM-side breakdown of each MoE layer: [M0-PROF] moe_layer[i] … router= topk= gather= ffn= route= scatter= in µs. Prints the same stages under moe_engine=cpu, so CPU vs HTP can be subtracted.lfm2_moe_layer.cpp:41–80, 432–439
NNTR_L2_DIFF=1Runs both MoE FFN paths and reports their difference (SNR); the accuracy gate's (b).htp_compute_ops.cpp:571–574; contract §1 accuracy row
NNTR_MOE_HTP_DECODE=1Measurement-only: on a plain QS4CX (non-WH) model, lets the listed layers take the HTP kernel at M==1 instead of the CPU. Not for the WH model (which has no choice).lfm2_moe_layer.cpp:498–504
--profile buildA separate app build that prints a [PROFILE] per-node table. Never read tok/s from it — it inflates prefill by 83 %. Per-token cost of a node type is computed as (sum at G=512 − sum at G=64) / 448.LEDGER rule 1; 77-first-handoff.md step 4

Two reading rules: read min, not avg, from profiles (averages include the first, registration-heavy call); and never compare tok/s across sittings or units — every sitting starts with the unchanged control binary and results are read as an A/B inside it. LEDGER rules 2, 9, 10, 13

8. What "healthy" looks like

On unit R3CY205ZMND, prompt 512, 8 threads (the only filled handoff so far): CPU model decode 46–54 tok/s, prefill 231–336 tok/s; NPU model decode 17–21 tok/s, prefill 403–541 tok/s; peak RSS ≈ 5.0–5.9 GB; two runs of one model print identical text. Full table on page 3. 77-first-handoff.md §A
