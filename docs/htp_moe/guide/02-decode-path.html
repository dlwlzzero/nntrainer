2. The decode path — what happens for one token, in order

Applications/CausalLM/models/lfm2/lfm2_causallm.cpp (layer graph), Applications/CausalLM/models/lfm2_moe/lfm2_moe_layer.cpp (router, gate, routing arrays), nntrainer/tensor/htp_backend/htp_compute_ops.cpp (the ARM side of the call), nntrainer/tensor/htp_backend/hmx/hexkl_mm_u8i4_moe.c (the DSP kernel), test/htp/nntr_hvx.idl; the PR's own walk-through docs/htp_attention/49_ffn_on_npu_report.md §2–§4 and cause analysis 48_decode_35_to_15_cause.md §3 (Korean, translated); numbers from docs/measurements/77-first-handoff.md §B and §A-profile, 94-sitting2-anchor-trace.md §B–§C, 88-moe-call-marshalling.md (transport after PR #103) and 105-m1-gemv-compute.md @ da41340b (the GEMV path's feed vs compute); the per-token budget from LEDGER §2 (cycle 9 row).

Decode means: the prompt has already been read (prefill), and the model now produces one token, feeds it back, produces the next, and so on. Every step below is repeated per token. The shape that matters everywhere is M = 1: one activation row goes through every matrix.

2.1 One token through the 24 layers

The new token's embedding row (Q4_0, 2048 wide) enters layer 0. Each layer is a mixer followed by a feed-forward block, each wrapped in an RMSNorm and a residual add. There are two mixer kinds and two feed-forward kinds:

  • Conv mixer (18 layers). rms_norm → in_proj (a fully-connected matrix to 3 × conv width) → split into three → custom_multiply (gate B) → causal_conv1d (a short depthwise convolution over the last few positions) → custom_multiply (gate C) → out_proj (fully-connected back to 2048). lfm2_causallm.cpp:152–201
  • Attention mixer (6 layers). q/k/v projections, per-head norm (reshaped_rms_norm), rotary position encoding (RoPE, rope_theta at lfm2_causallm.cpp:130), mha_core over the KV cache, o projection.
  • MoE FFN (22 layers). rms_norm → router → 4 of 32 experts → weighted sum. This is the block that runs on the DSP (§2.2). lfm2_causallm.cpp:212; contract §1
  • Dense FFN (2 layers). gate/up FCs → swiglu → down FC, on the CPU.

After layer 23: output_norm and the tied lm_head (output_of_causallm, 128 000 × 2048, Q4_0) give the logits; greedy decoding picks the argmax. lfm2_causallm.cpp:404; contract §1 "tied lm_head"

2.2 The MoE call, step by step

a. Router (ARM)

The normalized row x (2048 floats) is multiplied by the router matrix (FP32, 32 columns, on the CPU) to get 32 logits. For each expert the code takes a sigmoid; adds a per-expert bias only for ranking; keeps the top 4 by (sigmoid + bias); and sets each chosen expert's weight to its bias-free sigmoid divided by the sum of the four (then a fixed scaling factor). lfm2_moe_layer.cpp:271–312 (buildExpertAssignments), :774 (input.dot(gate_weights))

b. The gate: who runs the experts

tryMoeLayerOnAccelerator decides. If the expert weights are QS4CX_WH, the DSP path is taken even at one token, because no CPU kernel can read that layout. With plain QS4CX weights a single token would stay on the ARM (the 64-row padding does not pay) unless NNTR_MOE_HTP_DECODE=1. lfm2_moe_layer.cpp:455–506

A second switch decides which kernel path the DSP takes once the call arrives. NNTR_MOE_HTP_M1_GEMV is read once on the ARM and sent once per session through the IDL method moe_set_opts; the DSP stores the bit and decides per call on M (§2.2 e′). Since PR #108 (merged 2026-09-22) the GEMV path is on unless the variable is 0. The ARM prints [HTP] moe m1 gemv: on (applied=0x1) source=default (or source=env, or off for the opt-out) to stderr, which is the proof of the path a tok/s run took. With the path on, a skel that does not know the method makes the app throw with a rebuild hint rather than silently run the HMX loop. htp_compute_ops.cpp:1102–1143 (sendMoeOptsOnce); htp_moe_opts.h; test/htp/nntr_hvx.idl:443–449; test/htp/nntr_hvx_mm_u8i4.c:1065–1066

c. Routing arrays and staging (ARM)

The four (expert, weight) pairs become three arrays in expert order: row_index (which token row — at decode always row 0, four times), row_count[32] (1 for the four chosen experts, 0 elsewhere) and row_weight. The activation row (2048 floats = 8 KiB) is copied into a shared ION buffer the DSP can see; the output goes to another. Expert weight handles (small integers registered at load) are looked up from a cache. lfm2_moe_layer.cpp:524–545; htp_compute_ops.cpp:1723–1731

Which buffer, since PR #103 (#88): one per size class. Before, the app kept one activation buffer and one output buffer and grew them to the largest call ever seen (ensureCapacity) — after a 512-token prompt, 4 MiB each — and every later call reused them. Now stage() keeps a separate buffer for every power of two from 64 KiB up and hands each call the smallest one that fits: decode rides a 64 KiB pair, prefill a 4 MiB pair, and both stay allocated. Why that matters is in step d. htp_compute_ops.cpp:1464–1486 (StagingPool, stage); upstream fb0f02b9; 88-moe-call-marshalling.md staging: lines

d. FastRPC round trip

One remote call, nntr_hvx_mm_u8i4_moe_layer(session, M=1, K=2048, inter=1792, N_out=2048, h_gate_up[32], h_down[32], row_index, row_count, row_weight, act_f32, out_f32), blocks the ARM thread until the DSP returns. The stub (generated from nntr_hvx.idl by qaic) packs the small arrays (≈ 14 KB at prefill, a few hundred bytes at decode) and passes the ION buffers zero-copy; the driver wakes a DSP thread; the skel unpacks and calls the kernel. When NNTR_HTP_PROFILE ≥ 2 the _timed twin is used, which returns per-stage microseconds. test/htp/nntr_hvx.idl:161–182; htp_compute_ops.cpp:1470–1500

The session itself is opened once at load: an unsigned process domain on the compute DSP (cdsp), then a latency setting for poll mode (RPC_POLL_QOS, fallback PM_QOS); that is the qos_mode=2 in every profile header. htp_backend.cpp:40–110

Two costs hide in the round trip besides the work itself (plan 88's inventory, confirmed by #88's sitting):

  • Keeping the shared buffers consistent. The staging buffers are cached ION memory: the ARM writes the activation into its cache, so before the DSP reads it the driver must write the cache back to DDR (clean), and before the ARM reads the output it must drop stale cache lines (invalidate). The driver does this over the whole buffer, not the bytes passed — about 36–59 µs per MB on the PR author's phone. With the old 4 MiB pair every decode call paid for 8 MiB of cache maintenance to move 16 KiB. Size classes shrink that to two 64 KiB buffers.
  • How the ARM waits. After sending the call the ARM thread can poll — check the reply flag over and over in a tight loop, which notices the answer within microseconds but keeps a core busy — or sleep and be woken by an interrupt, which is cheap for the CPU but slow to wake. The poll window says how long to poll before switching to sleep. It was 100 µs; a decode call lasts ≈ 1.4 ms, so every call ended on the slow interrupt path. Since PR #103 the window is 5000 µs (NNTR_HTP_POLL_US), so the ARM is still polling when the DSP finishes.

Measured in one sitting (#88, M==1, profile level 2, µs per call): control A 401.3; C = the fixed binary with the poll forced back to 100 µs 155.5; B = both fixes 87.9. So of the 313.4 µs removed, 245.8 (78 %) is the staging and 67.6 (22 %) the poll. The remaining 88 µs is 6 % of the 1471 µs call and the 464 argument bytes are already the floor, so the planned "prebind" of per-layer handles was not built. docs/plans/88-moe-call-marshalling.md "What the 528 µs are", §2.1; 88-moe-call-marshalling.md Transport table and Verdict; LEDGER ⑦; htp_backend.cpp:76–92; doc 50 §3.6 via plan 88

e. On the DSP (hexkl_mm_u8i4_moe_layer_run): the HMX path

This is the path the PR shipped with; since PR #108 a decode call takes the vector-unit branch of e′ instead, and the HMX path serves prefill and the NNTR_MOE_HTP_M1_GEMV=0 opt-out. Steps 1–4 and the stage-out are shared. The stage names in brackets are the columns of the [HTP-PROFILE] M==1 row; the microseconds are #77's level-3 (5× repeat, min) values on the unit used, R3CY205ZMND; sitting 2 (#94) reproduced every DSP column on the same phone within 4 % (dsp 1222.7 → 1271.6, mm 746.6 → 781.9). hexkl_mm_u8i4_moe.c:573–1246 read with doc 49 §4.5 B-3…B-6; 77-first-handoff.md §B level 3; 94-sitting2-anchor-trace.md §B

  1. Validate and lay out. Every handle's K/N is checked before any work; VTCM (the DSP's 8 MiB on-chip scratch memory) is carved into fixed regions: activation block 128 KB, gate_up weights 3.5 MiB, down weights 1.75 MiB, gate f32, mid u8, two 256 KB accumulator staging buffers, result f32. :490–571, :597–613; doc 49 §4.4
  2. Stage in [stage 4.4 µs]: DMA the activation row from the uncached ION buffer into a cached DSP-heap copy act_c; zero out_c. :807–809
  3. Kick the first weight DMA. Expert 0's gate_up (3.5 MiB) is pushed from the ION arena (where all 1408 expert weights sit in DDR, in HMX tile order) into VTCM through a ring of 2D DMA descriptors, in four column chunks. :823–827, moe_push_gate_up_chunks :159; hexkl_dma_ring.c
  4. Activation quantization [quant 21.9]: the row's min/max give a scale and zero point; the row is packed as u8 into the "AH" tile layout the matrix unit reads. Each active expert gets a 64-row slot block; at M = 1 the other 63 rows are padding that repeats row 0. :831–872
  5. Per expert (4 times):
    • [gather 122.6] wait for the activation block DMA and copy the block's scale/zp;
    • push the expert's down weights (1.75 MiB) so they arrive during gate_up;
    • [drain 0.9+0.4] wait for the gate_up chunk;
    • [mm 746.6 + acc 258.8] HMX gate_up: for each of 112 column tiles, clear the accumulator, issue 64 tile multiplies (64 rows × 32 k × 32 n each), read the 64×32 int32 result out to staging. 63 of the 64 rows are padding at decode;
    • [dequant 7.3, swiglu] worker threads dequantize gate and up tiles (scale · column sum · bias) and store silu(gate) · up as f32;
    • [requant 41.9] the 1792-wide f32 row becomes u8 again for the down matrix (synchronous, nothing to hide behind);
    • HMX down (same shape rules, 64 column tiles) → dequantize to f32;
    • [scatter 0.9] out_c[row] += weight · result — the weighted sum of the four experts is this +=. :976–1225; doc 49 §3.2.2 "scatter"
  6. Stage out: DMA out_c back to the ION output buffer; return. :1230–1246

Sum: dsp 1222.7 µs per call, of which the weight DMA moved 21 504 KB at 18.0 GB/s averaged over the call; host 1750.4 µs; the difference, transport 527.7 µs, is the round trip. (Level 2, without repetition: host 1948.6 / dsp 1360.9 / transport 587.7, DMA 16.2 GB/s.) 77-first-handoff.md §B

e′. The M = 1 path on the vector unit (PR #86; the decode default since PR #108)

This is what a decode MoE call runs today. Wall 1's fix lives inside the same kernel as a branch taken right after the activation scan: when the session flag is set (the default since PR #108) and the call has at most 4 rows, at most 4 rows per expert and 1–16 active experts, the HMX loop and every weight DMA are skipped and the four experts go through the HVX matrix-vector kernel (hvx_gemm_u8i4_wh_col, the one the prefill "tail" path already used). It reads the WH weight tiles straight from the ION arena with vector loads behind an l2fetch prefetch — no VTCM staging — and produces the same int32 sums as the HMX, because integer sums do not depend on order. The output is therefore byte-equal to the HMX path: the host check prints M1 GEMV PATH BIT-IDENTICAL TO HMX PATH (M=1,2,4; tiny+real) and the device gtest MoeLayerM1GemvMatchesHmx runs the same call with the flag off and on and requires memcmp == 0. A prefill call (M > 4) never sees the branch, so prefill is untouched by construction. hexkl_mm_u8i4_moe.c:426–440 (rules and bounds), :807–810 (use_m1), :1019–1024 (first gate_up push skipped), :1052–1131 (the path); test/htp/host/moe_layer_host_check.c:708; test/unittest/unittest_hvx_mm_u8i4.cpp:2274–2280; docs/plans/80-m1-moe-gemv-dispatch.md §3

Three barriers on the worker pool, then an inline scatter, no background jobs. The pool's lanes are the HVX contexts the DSP reports minus one, plus the calling thread — 6 lanes on v79 per plan 105. (The kernel comment and earlier versions of this guide said "four HVX contexts"; the code sizes the pool from qurt_hvx_get_units() at session open, and plan 105 corrects the comment.) test/htp/hvx_add_f32.c:108–118; plan 105 §2, §2 file table

  1. Pack [quant]: each expert's rows are packed into its slot block inline (≤ 16 rows), no 64-row padding job.
  2. Stage A [mm, worker time in swiglu]: one pool run over 4 experts × 56 column pairs = 224 units; each unit multiplies the row by one gate column and its up column (GEMV), then dequantizes and stores silu(gate) · up as f32.
  3. Stage B [requant]: one run over the 4 experts; the 1792-wide f32 row becomes u8 for the down matrix — same functions and arguments as the HMX path's requant.
  4. Stage C [mm]: one run over 4 × 64 down column tiles; dequantize to f32.
  5. Scatter [scatter]: out_c[row] += weight · result, expert order, row order — the exact add sequence of the HMX path's scatter worker, so the f32 bytes match.

Profile signature of the path: blocks=0, dma_kb=0, acc, dequant and drain 0, the new PATH slot = 1, and on the ARM the [HTP-PROFILE] M==1 row ends in m1_gemv=<calls>/<calls>. The arena read rate is 22 MB / mm. Scratch: about 261 KB per expert, reserved for the 16-expert bound (≈ 4.2 MB of the DSP heap), never regrown. hexkl_mm_u8i4_moe.c:1094–1099 (probe convention), :896–906 (scratch); htp_compute_ops.cpp:590–599 (the m1_gemv= field); plan 80 §3.3, §3.6

What it was expected to cost. Per call the four experts are 22.0 MB of weights; read at the in-call 18 GB/s that is 1.22 ms, at the PR author's 38 GB/s probe 0.58 ms, plus 0.16–0.35 ms of HVX work (the GEMV issues all four row accumulators even at one row; three are dead). So dsp was expected at 0.7–1.4 ms against the HMX loop's 1.35 — wall 1 falls either way (blocks=0), and the number that comes out is the arena read rate. The open risk the kernel comment names: the arena is CPU-uncached ION mapped into the DSP, and whether vector loads from that mapping are cached (so that l2fetch helps) had never been measured. plan 80 §3.4 and §6 first row; hexkl_mm_u8i4_moe.c:434–437 (ponytail: note)

What it cost on the phone (#94 sitting 2, variant C, 2026-09-22). Same binary, NNTR_MOE_HTP_M1_GEMV=1, read against the same sitting's A: decode +6.2 / +7.7 / +1.7 % at gen 64 / 512 / 1024 (18.83 / 18.33 / 17.59 vs 17.72 / 17.03 / 17.30 tok/s), text byte-identical at every cell, device gtest bit-identical (0 bad of 2048 and 8192). Where the 975 µs go — measured by #105 (2026-09-22). Reading the compiled inner loop, plan 105 found that at one row the kernel still runs the four-row loop: per 32×32 weight tile it issues 32 vrmpy multiply-accumulates (only 8 are for the real row) rotating over four accumulators, and each column's l2fetch prefetch goes out right before the loads that need it. PR #107 replaced it with a one-row loop (gemm_row1, the same accumulation order, so bit-identical by construction) and a prefetch lead, so each lane fetches its next block of columns early (0, 64 or 192 KB ahead: variants B1, B2, B3). A microbench, MoeM1GemvFeedVsCompute, runs the same kernel on three copies of the weights — the ION arena, the ordinary DSP heap, and a set small enough to stay hot in the L2 cache — so the hot cell shows the arithmetic alone and the gap to the arena cell shows the waiting.

What the phone said. The arithmetic got 2.26× faster (hot cell 70.77 → 31.25 ns per tile) — but on the arena the one-row loop was slower without a lead (mm +7.4 %), and even the 192 KB lead only reached −4.3 % (973.0 → 930.9 µs), short of the gate (more than −5 %, and ≤ 600 µs to close the item). Decode moved −8 % to +3 %; text stayed identical in every cell. The reason is the feed: under the one-row loop with the 192 KB lead, ≈ 74 % of mm is waiting for weight bytes (≈ 690 of 931 µs), only ≈ 240 µs is arithmetic. A vector unit that reads DDR directly gets 21–27 GB/s whether the weights sit in the ION arena or in the DSP heap, and with a quarter of the multiply-accumulates in flight the one-row loop hides that latency worse (LEDGER rules 26, 27). So PR #107 is held, not merged, and the next step is to feed the GEMV from VTCM: DMA each expert's weights into on-chip memory while the vector unit works on the previous one. That needs a DMA shape that moves ≥ 37 GB/s beside the vector unit (22 MB in ≤ 600 µs) — exactly what #100 now certifies — and then the one-row loop's ≈ 240 µs of arithmetic hides comfortably under the feed, where the four-row loop's ≈ 590 µs would not. docs/plans/105-m1-gemv-compute.md §1, §3; 105-m1-gemv-compute.md Verdict, "What the microbench says"; LEDGER §2 ㉒ row, rules 26–27; plan 100 §0

2.5 After the walls: one call per token

Today's token at G=512 is ≈ 37.2 ms: MoE DSP ≈ 22.7, transport ≈ 4.0, everything outside the MoE calls ≈ 10.5 (LEDGER's cycle-9 estimate). Even if the VTCM feed brings the MoE calls to ≈ 14.5 ms, the transport plus the outside time must fall to ≈ 5.5 ms for the 20 ms that 50 tok/s needs. The contract's next step is therefore M = 1 kernels for the rest of the layer on the DSP (RMSNorm, conv1d + gating, RoPE, attention at M = 1, dense FFN, lm_head) and one per-token entry in the IDL, so the ARM sends one token in and gets logits out with a single round trip — the "DSP owns the graph" shape that the frozen hvx_impl branch already validated for a smaller model. Plan 85 now designs the skeleton (a forward entry with a validated op table) and says plainly that it saves nothing on its own: the call count only drops once every op between two MoE layers is resident, including the FC projections, the router and lm_head, which no issue covers yet. contract §2, §3.1 step 3; LEDGER §2 budget row (cycle 9), §3 ⑨ and §4; docs/plans/85-per-token-entry-skeleton.md §0; issues #81 #82 #85
