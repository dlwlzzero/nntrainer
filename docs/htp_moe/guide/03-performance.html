What it means, in plain words. The vector-unit (HVX) matrix-vector kernel that runs the four experts at decode spends most of its time waiting for weight bytes to arrive from main memory, not computing. PR #107 made the arithmetic 2.26× cheaper, but that only shows when the weights are already in the DSP's cache; reading them from the ION arena in DDR, the cheaper loop has fewer loads in flight and gets slower unless it prefetches far ahead. So the next lever is the feed: copy each expert's weights into VTCM by DMA while the vector unit computes (#100 certifies a DMA shape that can do it; then a feed issue builds it on top of #107's loop). PR #107 is held, not merged. Since this sitting PR #108 made this GEMV path the default (merged 8e121dbe): the next sitting's A runs it with the variable unset. #105's A and #88's B (24.50 / 23.80 / 23.52, GEMV off) come from different sittings, so their gap is not a verdict (rules 9, 20). Prefill: every variant's prefill DSP time (M>1 dsp) is within 2.5 % of A, so the gate holds even though the tok/s column fell with the phone's temperature. generation(last 64) is still not printed (#89).

Why #99 does not undo the replay numbers (plan 99, 2026-09-22)

Every one of the 11 MoeChunkReplay cells ended checksum_ok=n with the same two numbers (res[6] 1 467 840 vs want_sum 9 461 760, ratio 6.446), and bytes_per_call read 22 560 768 where the handoff expected 22 020 096. Plan 99 read the code and found three separate facts: (1) the kernel writes each gate/up chunk into VTCM strided — destination stride = source stride = 57 344 B, so an expert's eight chunks tile a 3 670 016 B window exactly once — while the replay passed destination stride = row size, so the chunks landed packed and overlapping in a 569 344 B window; the skel summed the packed window (8 896 samples × 0xA5 = 1 467 840) and the host the kernel's (57 344 × 0xA5 = 9 461 760); (2) 22 560 768 is correct — it is 22 020 096 of weights plus 524 288 of activation blocks plus 16 384 of copies, and the in-situ weight DMA: line counts weights only; (3) regions=32 is the fresh=1 rotation pool, not the expert count. The DDR read stream — source addresses, strides, row sizes, byte counts, order and the 30 wait points — was byte-for-byte the in-situ one; only the VTCM write geometry differed, and DMA_PROBE shape iii writes packed too, so packing cannot be what separates 40.2 from 106.9 GB/s. Under this diagnosis rows c, d, g and h stand as measured; the fix (replay with the kernel's destination stride, print weight_bytes beside bytes_per_call, a host check that pins the footprint arithmetic) rides along in the next handoff, and cell 1 within ±10 % of 561.5 µs confirms h.
