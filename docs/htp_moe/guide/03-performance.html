Why #99 does not undo the replay numbers (plan 99, 2026-09-22)

Every one of the 11 MoeChunkReplay cells ended checksum_ok=n with the same two numbers (res[6] 1 467 840 vs want_sum 9 461 760, ratio 6.446), and bytes_per_call read 22 560 768 where the handoff expected 22 020 096. Plan 99 read the code and found three separate facts: (1) the kernel writes each gate/up chunk into VTCM strided — destination stride = source stride = 57 344 B, so an expert's eight chunks tile a 3 670 016 B window exactly once — while the replay passed destination stride = row size, so the chunks landed packed and overlapping in a 569 344 B window; the skel summed the packed window (8 896 samples × 0xA5 = 1 467 840) and the host the kernel's (57 344 × 0xA5 = 9 461 760); (2) 22 560 768 is correct — it is 22 020 096 of weights plus 524 288 of activation blocks plus 16 384 of copies, and the in-situ weight DMA: line counts weights only; (3) regions=32 is the fresh=1 rotation pool, not the expert count. The DDR read stream — source addresses, strides, row sizes, byte counts, order and the 30 wait points — was byte-for-byte the in-situ one; only the VTCM write geometry differed, and DMA_PROBE shape iii writes packed too, so packing cannot be what separates 40.2 from 106.9 GB/s. Under this diagnosis rows c, d, g and h stand as measured; the fix (replay with the kernel's destination stride, print weight_bytes beside bytes_per_call, a host check that pins the footprint arithmetic) rides along in the next handoff, and cell 1 within ±10 % of 561.5 µs confirms h. Plan written, not yet implemented at this commit. docs/plans/99-replay-content-check.md §1, §3 "Root cause", "Verdict on the provisional rows"; issue #99; LEDGER ⑳

#94 first attempt — the skel that would not load (2026-09-22 morning, unit used R3CY205ZMND, filled at ec7ad296)
