What it means, in plain words. #105 had left one cheap hope: the prefetch lead (l2fetch, asking the cache for weight bytes ahead of time) kept helping up to 192 KB, and the loop the phone actually runs by default (four rows at a time) had never been tried with any lead. #113 put the whole 2 × 5 grid — two loops × leads of 0 / 192 / 384 / 768 / 1536 KB — on one skel and measured it in one gtest run. The answer is the opposite of the hope: the four-row loop is harmed by any lead, by 2.1–2.5× from the very first non-zero value, while a copy of the weights that already sits in cache is unaffected — so the prefetch is not evicting useful data, it is competing with the loop's own loads for the same cache and bus. Only the one-row loop, which has fewer loads in flight and is therefore waiting on latency, gains from the lead, and only up to 192 KB. In the layer call that best cell, D192, reads mm 937.0 µs against 1000.2 — a 6.3 % cut, short of the 840 µs gate, and the same number #105 had already measured for it (930.9). So the gate fails on every cell and nothing on the board is left that could pass. End to end, though, D192 decoded 3.3–4.3 % faster at all three lengths with byte-identical text and a clean prefill. The user decided to land it anyway (rule 33: a sub-gate win may become the default when it is consistent at all three G, text-identical and prefill-clean; the issue's own gate still says the issue is not done). PR #115 therefore flips the two build defaults to D192; PR #107 closes with its machinery kept; the "now" stays #100 A until a sitting whose A is the flipped default. The ride-along closed the other question: the DMA cell nobody touched read the same 31 GB/s as #100 on a cold phone, so #94's 40 GB/s day is not coming back and the VTCM feed (㉒'s other half) is worth what #100 measured — 31.6 GB/s beside HVX vs 23.5 for D192's direct read, ≈ 1.33× — filed as #117, gate mm ≤ 760. Thermal note: the profiles ran 27.5 → 57.7 °C in issue order and D192, the hottest cell, was still the fastest, so no ordering in the table is heat. generation(last 64) is still not printed (#89).
