Making an 8-billion-parameter model decode on a phone's NPU

this page: docs/plans/0001-htp-moe-decode-agent-system.md §1–§3, docs/htp_moe/BENCHMARK.md "Goals", docs/htp_attention/48_decode_35_to_15_cause.md §1 (Korean, translated here).

What the project is

The project runs the language model LFM2.5-8B-A1B on a Galaxy S25 Ultra (Snapdragon 8 Elite) and moves the heaviest part of every step onto the phone's signal processor (the Hexagon HTP, Qualcomm's name for the NPU built around a DSP). The model has 24 layers — 18 "conv" layers and 6 attention layers — and 22 of them carry a mixture-of-experts feed-forward block (MoE FFN): 32 small expert networks of which every token uses only 4. Hidden width is 2048, the vocabulary 128 000 words, and the output projection (lm_head) is tied to the input embedding. contract §1, model row (from the model's config.json)

The starting point is an upstream pull request (nntrainer PR #4327) that already runs the MoE FFN on the HTP and wins at prefill — reading the prompt, many tokens at once. This guide is only about decode: producing one new token at a time, where the NPU path is still slower than the CPU. The goal: decode at ≥ 50 tokens per second on the NPU at every generation length, which is about 2.4× the PR's own NPU number and above the phone's CPU. contract §1 "Goal" row (user decision Q1 ii)

The one-paragraph mental model

One token = read 730 MB of weights. During decode there is one token, so every matrix multiply is a matrix times a single vector. Arithmetic is nearly free; what costs time is pulling every weight byte the token touches out of the phone's main memory (DDR). For this model that is about 730 MB per token: the 4 active experts in each of 22 MoE layers (484 MB), the conv and attention projections (≈ 170 MB) and the lm_head (75 MB). The memory can deliver 34–38 GB/s, so the floor is 19–21 ms per token, i.e. 48–52 tok/s is the physical ceiling, and the CPU already sits on it. To match or beat it, the DSP must (1) read the weights as fast as the memory allows and (2) be called once per token, because every ARM↔DSP call costs about half a millisecond and 22 of them per token is already 12.5 ms. doc 48 §1 (byte table), contract §1 "Physical ceiling", doc 48 §3 (transport 0.57 ms × 22)

Why the NPU is slow today — three walls

The PR's own device work measured one MoE layer call at decode: 1.91 ms on the host, of which 1.35 ms is DSP work and 0.57 ms is the ARM↔DSP round trip. Three things hide in that number, and all three must fall — removing any one alone leaves the call about where it is (see page 2):

  1. The matrix unit computes 64 rows for 1 row. The HMX tile is 64 rows tall; decode has one row, so 63/64 of the work is padding: 1.03 of the 1.35 ms. Fix: a vector-unit (HVX) matrix-vector kernel for M ≤ 4 — built and measured (PR #86, switch NNTR_MOE_HTP_M1_GEMV=1; #94 sitting 2 variant C, 2026-09-22): decode +6.2 / +7.7 / +1.7 % at gen 64 / 512 / 1024, text identical, DSP time per call 1414 → 1044 µs and the DMA wait gone from the call — but the GEMV's own read of the 22 MB from the arena (mm 783 → 975 µs) is now the cost. Next: make it the default (#101) and feed it from VTCM (LEDGER ㉒). See page 2 §2.2 e′.
  2. Weight DMA runs at 16–18 GB/s inside the layer call while the same engine reaches 72–117 GB/s in an isolated probe. Measured where the loss is (PR #93's trace, #94 sitting 2): the engine runs at 22–32 GB/s while busy and is rarely waited on, so it is not serialised behind compute; the real 46-descriptor list of one call, replayed with no compute at all, reaches only 40 GB/s where a probe of the identical per-descriptor shape does 107 GB/s on the same phone and skel. About 2.7× is lost inside the descriptor list or region layout itself (row h → #100, blocked by the replay harness's content-check bug #99, whose cause is known and does not change the timings); the rest is the un-hidden first expert and a cold-call penalty (≈ 20 % of DSP time).
  3. The round trip costs 0.53–0.59 ms per call, 22 calls per token = 11.6–12.9 ms. The plan for #88 (2026-09-22) reads the code and two upstream measurements and finds the cost is not the arguments (≤ 0.5 KiB per call) but (a) the FastRPC driver's cache clean/invalidate over the two staging buffers, which are sized by the prompt (4 MiB + 4 MiB) although decode uses 8 KiB of each, ≈ 290–470 µs, and (b) a 100 µs poll window after which the call falls back to an interrupt wait. Fix: size-class staging and a 5 ms poll window (two upstream commits), then one call per token. Planned, not yet built; sitting 2 measured the transport at 649–668 µs/call in A and 748 in C (+100 µs, unexplained — #88 reads it).

How the work is organised

  • Decode first, NPU-only first. Order: measure (done, #77 and #94) → the three walls in the order the measurements dictate (wall 1's fix is measured at +6–8 % and about to become the default; wall 2's cause is located in the descriptor list, fix pending #99/#100; wall 3 is planned) → one FastRPC call per token with the whole layer stack resident on the DSP → prefill residency later. contract §3.1–3.2; LEDGER §3
  • Every performance claim comes from a handoff: a document the user runs on the phone in one sitting, always as a full-model end-to-end run, always with the unchanged control binary first. Any S25 Ultra may be used; the handoff names no serial and the filled copy records the one used. contract §4.2, §12 (2026-09-22)
  • No Hexagon simulator: kernels are proven by host scalar checks (bit-identity) and then by the device. contract §4.1, decisions log
