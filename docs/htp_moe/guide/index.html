What the project is

The project runs the language model LFM2.5-8B-A1B on a Galaxy S25 Ultra (Snapdragon 8 Elite) and moves the heaviest part of every step onto the phone's signal processor (the Hexagon HTP, Qualcomm's name for the NPU built around a DSP). The model has 24 layers — 18 "conv" layers and 6 attention layers — and 22 of them carry a mixture-of-experts feed-forward block (MoE FFN): 32 small expert networks of which every token uses only 4. Hidden width is 2048, the vocabulary 128 000 words, and the output projection (lm_head) is tied to the input embedding. contract §1, model row (from the model's config.json)

The starting point is an upstream pull request (nntrainer PR #4327) that already runs the MoE FFN on the HTP and wins at prefill — reading the prompt, many tokens at once. This guide is only about decode: producing one new token at a time, where the NPU path is still slower than the CPU. The goal: decode at ≥ 50 tokens per second on the NPU at every generation length, which is about 2.4× the PR's own NPU number (20.8) and above the phone's CPU. Today the NPU decodes at 27.89 tok/s at 512 tokens (#117 variant A, 2026-09-23, on the second phone R3CY10WM83Y), so the distance is 1.79×. The same sitting measured the next default — the expert weights streamed into the DSP's on-chip memory by DMA (the VTCM feed, PR #118, merged the same day) — at 36.49 tok/s, +30.9 % with identical text; it becomes the "now" only once it is measured as a sitting's own control, and then the distance is 1.37×. contract §1 "Goal" row (user decision Q1 ii); BENCHMARK.md "Goals", NPU row and the Method note on the feed default; 117-m1-gemv-vtcm-feed.md "Second sitting"; contract §1 "Now" and "Goal" rows

The one-paragraph mental model

One token = read 730 MB of weights. During decode there is one token, so every matrix multiply is a matrix times a single vector. Arithmetic is nearly free; what costs time is pulling every weight byte the token touches out of the phone's main memory (DDR). For this model that is about 730 MB per token: the 4 active experts in each of 22 MoE layers (484 MB), the conv and attention projections (≈ 170 MB) and the lm_head (75 MB). The memory can deliver 34–38 GB/s, so the floor is 19–21 ms per token, i.e. 48–52 tok/s is the physical ceiling, and the CPU already sits on it. To match or beat it, the DSP must (1) read the weights as fast as the memory allows and (2) be called once per token. Each ARM↔DSP call used to cost about half a millisecond (22 per token = 12.5 ms); #88 cut that to 0.09 ms. The vector-unit (GEMV) path that replaced the matrix unit for decode then read its 22 MB of weights per call straight out of DDR, and paid twice for it: ≈ 74 % of its matrix time was waiting for weight bytes (#105 — DDR latency, not a lack of bandwidth), and its round trip grew back to 0.19 ms (4.2 ms per token). Asking for the bytes earlier (the l2fetch prefetch lead) was measured to its end by #113: it helps only the one-row loop, only up to 192 KB, and that best cell (D192, the default since PR #115) cuts the matrix time by 6.3 % — a consistent +3–4 % in decode. #117 then did (1) properly: while the vector unit works on one expert, the DSP's DMA engine copies the next expert's weights into on-chip memory (VTCM), and the loop reads the copy. On the phone the matrix time per call fell 932 → 676 µs with the engine busy 90 % of the call at 32–34 GB/s, the round trip fell 190 → 92 µs (the extra transport had been the arena read's, not the path's — rule 35), and decode rose +29–32 % at every length with identical text, twice. That feed is the default since PR #118 (2026-09-23). One caveat: the DMA rate is per phone — the unit #117 ran on moves 37.3 GB/s where the earlier unit moves 31.2 (rule 34), so there the same feed is worth ≈ +10 %. After that only (2) remains, and it is now the larger half: transport 2.0 + the ≈ 9.7 ms of CPU work around the 22 calls = 11.7 ms per token against a ≈ 6.5 ms floor, which only one call per token with the whole layer stack on the DSP removes. doc 48 §1 (byte table), contract §1 "Physical ceiling", doc 48 §3 (transport 0.57 ms × 22); LEDGER §2 per-token budget rows (cycle 7, GEMV off: transport 22 × 0.088 = 1.9 ms; cycle 11, GEMV default: transport 22 × 0.186 = 4.1 ms, outside the MoE call ≈ 9.9 ms at G=512 — estimates derived from tok/s); LEDGER ㉒ rows (cycles 12, 15), cycle-15 budget row (B 27.40 ms = MoE dsp 15.7 + transport 2.0 + outside 9.7), rules 26, 28–35; 113-m1-gemv-lead-matrix.md Verdict, "Landed defaults"; 117-m1-gemv-vtcm-feed.md Profiles, "Second sitting", Verdict, "Landed defaults"

Why the NPU is slow — three walls: all three have fallen inside the call; what is left is outside it

The PR's own device work measured one MoE layer call at decode: 1.91 ms on the host, of which 1.35 ms is DSP work and 0.57 ms is the ARM↔DSP round trip. Three things hide in that number, and all three must fall (see page 2):

  1. The matrix unit computes 64 rows for 1 row. The HMX tile is 64 rows tall; decode has one row, so 63/64 of the work is padding: 1.03 of the 1.35 ms. Fix: a vector-unit (HVX) matrix-vector kernel (GEMV) for M ≤ 4 — built (PR #86), measured (#94 sitting 2: decode +6.2 / +7.7 / +1.7 %, text identical) and the default since PR #108 (merged 2026-09-22; NNTR_MOE_HTP_M1_GEMV=0 turns it off). The padding is gone, but the GEMV reads the 22 MB of weights per call straight from DDR at ≈ 22.6 GB/s, and #105 measured that ≈ 74 % of its time is waiting for those bytes: a cheaper inner loop (PR #107) is 2.26× faster when the weights are already in cache and no faster from DDR. #100 (2026-09-23) then measured the alternative — DMA the weights into the DSP's on-chip memory (VTCM) — at 31.6 GB/s, only ≈ 1.2× the direct read, on a day when the same phone's DMA ran 22 % slower than the day before on an untouched test cell. The user's direction after that: stop leaning on DMA numbers, take the compute-side wins. The wait is DDR latency (rule 26), and the one knob measured against it, the l2fetch prefetch lead, kept helping up to the largest value tried (192 KB) and was never tried on the loop the phone runs by default. #113 measured that whole loop × lead matrix on 2026-09-23 (one skel, one app, the loop and the lead picked by two environment variables): the four-row loop is harmed by any lead, 2.1–2.5× on the arena and unchanged when the weights are already in cache — the prefetch competes with the loop's own loads, it does not evict anything (rule 31) — and only the one-row loop gains, only up to 192 KB. That best cell, D192, reads mm 937.0 µs against 1000.2 (−6.3 %; the 840 µs gate is missed on every cell and nothing unmeasured could pass) yet decodes +4.11 / +3.29 / +4.26 % faster with byte-identical text, so the user landed it as the default anyway (rule 33, PR #115); PR #107 closed with its machinery kept. The compute side of the GEMV is exhausted: under a direct DDR read mm cannot go below ≈ 815 µs. The ride-along settled the other half: the DMA cell nobody touched read 31.2 GB/s on a cold phone, the same as #100, so 31–32 GB/s is that unit's DMA bound (rule 32) and the VTCM feed is worth ≈ 1.33× there. #117 built and measured it (2026-09-23, on the user's second S25 Ultra): each expert's two weight matrices are DMA'd into VTCM one expert ahead, into two slabs that alternate by expert, and the one-row loop reads the copy with its lead switched off. mm 931.9 → 676.4 µs (gate ≤ 760, passed in a warm and in a cooled sitting), the engine busy 90 % of the call at 32–34 GB/s, decode +32.5 / +30.9 / +28.6 % with byte-identical text in 36 of 36 runs, prefill untouched (the feed runs only at M = 1). Landed by the gate: PR #118 makes the feed the default (feed=vtcm in the banner; NNTR_MOE_HTP_GEMV_FEED=0 is the opt-out). The new fact under it: that phone's DMA engine reads 37.3 GB/s on the anchor cell against 31.2 on the earlier unit while its vector unit reads DDR at the same rate, so the feed's win is unit-dependent — ≈ +10 % projected on the slower phone (rule 34). What is left inside the call is ≈ 1.9 ms per token of engine gap on a fast unit (㉓, in-situ 32–34 vs 37.3), nothing on a slow one. See page 2 §2.2 e′.
  2. Weight DMA at 16–18 GB/s — dissolved as a descriptor-list problem (#100). Inside the old (HMX) layer call the DMA averaged 16–18 GB/s while the same engine reached 72–117 GB/s in an isolated probe, and #94 sitting 2 had located most of the gap in the call's own 46-descriptor list ("row h": replayed with no compute it did 40 GB/s where a probe of the same shape did 107). #100 measured the probe against a per-call cell whose content is checked (c_star): that validated ceiling is 26.3 GB/s, and the real list runs at 1.19× it — faster than the ceiling, so there was never a list-side loss to fix; the probe number was one no real per-call path can reproduce (rule 28; rule 11 amended, rule 19 withdrawn). The engine tops out near 31 GB/s on every validated cell whatever the descriptor count or shape. With the GEMV the default, the list is not on the decode path anyway (2 descriptors per call). What remains of wall 2 at decode is the read rate itself, which lives in wall 1's prefetch question.
  3. The round trip — closed on 2026-09-22 (#88). It cost 401 µs per call in #88's own control run (22 calls per token). Most of that was not the arguments (464 bytes per call) but two things: (a) the activation and output buffers had grown to the prompt's size, 4 MiB each, and the FastRPC driver keeps a whole cached buffer consistent between ARM and DSP on every call — so every decode call paid for flushing 4 MiB although it used 8 KiB; (b) the ARM waited for the answer by polling (spinning on a flag) for only 100 µs, and a 1.4 ms call always outlived that and fell back to the slower interrupt wake-up. Upstream's size-class staging (a 64 KiB buffer for decode) and a 5 ms poll window, merged as PR #103, took the transport to 87.9 µs per call (−78 %): 245.8 µs of the cut is the staging, 67.6 µs the poll. Decode rose +30.9 / +41.4 / +42.9 %, text identical, prefill −0.9 % (inside the −5 % gate). On the GEMV path #100 read the two paths in one sitting on one binary: 185.8 µs (GEMV) vs 84.6 (HMX) per call, +101 µs, with the same 64 KiB buffers — and the ledger booked it as the price of the path, to come back only with one call per token. That reading was wrong (rule 35): under #117's VTCM feed, the same binary and sitting read 190 → 92 µs per call, the HMX path's level — the extra transport belonged to the direct HVX read of the arena, not to the GEMV path, and ≈ 2.2 ms per token came back with the feed. Cause not separated (the arena read may leave the ARM-side cache maintenance or the dmlink sync more to do at the call boundary; the shorter call stays inside the poll window). Transport is now ≈ 2.0 ms per token at the feed default; the rest of it goes only with one call per token.

How the work is organised

  • Decode first, NPU-only first. Order: measure (done, #77 and #94) → the three walls in the order the measurements dictate (wall 3 closed by #88; wall 2 dissolved by #100; wall 1's GEMV is the default since PR #108, #105 showed it is waiting on its weight feed, #113 measured the prefetch lead to its end — D192 landed by decision (rule 33, PR #115) — and #117 fed the GEMV from VTCM by DMA: gate passed twice, +29–32 % decode, the default since PR #118) → one FastRPC call per token (#85 / PR #119 → #82 → #81, now the main lever: 11.7 of the 27.4 ms are transport and CPU work outside the MoE call) with the whole layer stack resident on the DSP → prefill residency later.
