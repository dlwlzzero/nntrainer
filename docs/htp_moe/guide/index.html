Making an 8-billion-parameter model decode on a phone's NPU

this page: docs/plans/0001-htp-moe-decode-agent-system.md §1–§3, docs/htp_moe/BENCHMARK.md "Goals", docs/htp_moe/LEDGER.md §2 (⑦, ㉒, the cycle-9 per-token budget row), rules 26–27, docs/measurements/105-m1-gemv-compute.md @ da41340b (branch htp/105-m1-gemv-compute), 88-moe-call-marshalling.md, docs/htp_attention/48_decode_35_to_15_cause.md §1 (Korean, translated here).

What the project is

The project runs the language model LFM2.5-8B-A1B on a Galaxy S25 Ultra (Snapdragon 8 Elite) and moves the heaviest part of every step onto the phone's signal processor (the Hexagon HTP, Qualcomm's name for the NPU built around a DSP). The model has 24 layers — 18 "conv" layers and 6 attention layers — and 22 of them carry a mixture-of-experts feed-forward block (MoE FFN): 32 small expert networks of which every token uses only 4. Hidden width is 2048, the vocabulary 128 000 words, and the output projection (lm_head) is tied to the input embedding. contract §1, model row (from the model's config.json)

The starting point is an upstream pull request (nntrainer PR #4327) that already runs the MoE FFN on the HTP and wins at prefill — reading the prompt, many tokens at once. This guide is only about decode: producing one new token at a time, where the NPU path is still slower than the CPU. The goal: decode at ≥ 50 tokens per second on the NPU at every generation length, which is about 2.4× the PR's own NPU number (20.8) and above the phone's CPU. Today the NPU decodes at 26.88 tok/s at 512 tokens, so the distance is 1.86×. contract §1 "Goal" row (user decision Q1 ii); BENCHMARK.md "Goals", NPU row

The one-paragraph mental model

One token = read 730 MB of weights. During decode there is one token, so every matrix multiply is a matrix times a single vector. Arithmetic is nearly free; what costs time is pulling every weight byte the token touches out of the phone's main memory (DDR). For this model that is about 730 MB per token: the 4 active experts in each of 22 MoE layers (484 MB), the conv and attention projections (≈ 170 MB) and the lm_head (75 MB). The memory can deliver 34–38 GB/s, so the floor is 19–21 ms per token, i.e. 48–52 tok/s is the physical ceiling, and the CPU already sits on it. To match or beat it, the DSP must (1) read the weights as fast as the memory allows and (2) be called once per token. Each ARM↔DSP call used to cost about half a millisecond (22 per token = 12.5 ms); #88 cut that to 0.09 ms on the old kernel path (today's GEMV path reads 0.18 ms, 4.0 ms per token, in #105), but the ≈ 10.5 ms of CPU work around the 22 calls is still there, and only one call per token with the whole layer stack on the DSP removes it. Today the biggest single piece is (1): the DSP spends ≈ 74 % of its matrix time waiting for weight bytes (#105). doc 48 §1 (byte table), contract §1 "Physical ceiling", doc 48 §3 (transport 0.57 ms × 22); LEDGER §2 per-token budget rows (cycle 7, GEMV off: transport 22 × 0.088 = 1.9 ms; cycle 9, GEMV on: transport 22 × 0.183 = 4.0 ms, outside the MoE call ≈ 10.5 ms at G=512 — estimates derived from tok/s); LEDGER ㉒ row and rule 26

Why the NPU is slow — three walls: one down, one reshaped, one off the decode path

The PR's own device work measured one MoE layer call at decode: 1.91 ms on the host, of which 1.35 ms is DSP work and 0.57 ms is the ARM↔DSP round trip. Three things hide in that number, and all three must fall (see page 2):

  1. The matrix unit computes 64 rows for 1 row. The HMX tile is 64 rows tall; decode has one row, so 63/64 of the work is padding: 1.03 of the 1.35 ms. Fix: a vector-unit (HVX) matrix-vector kernel (GEMV) for M ≤ 4 — built (PR #86), measured (#94 sitting 2: decode +6.2 / +7.7 / +1.7 %, text identical) and the default since PR #108 (merged 2026-09-22; NNTR_MOE_HTP_M1_GEMV=0 turns it off). The padding is gone, but the GEMV reads the 22 MB of weights per call straight from DDR at ≈ 22.6 GB/s, and #105 measured that ≈ 74 % of its time is waiting for those bytes: a cheaper inner loop (PR #107) is 2.26× faster when the weights are already in cache and no faster from DDR. So the remaining lever here is the feed — copy each expert's weights into the DSP's on-chip memory (VTCM) by DMA while the vector unit computes. See page 2 §2.2 e′.
  2. Weight DMA runs at 16–18 GB/s inside the old (HMX) layer call while the same engine reaches 72–117 GB/s in an isolated probe. PR #93's trace and #94 sitting 2 located most of it in the call's own 46-descriptor list: replayed with no compute, it reaches only 40 GB/s where a probe of the identical per-descriptor shape does 107 GB/s (row h). With the GEMV now the default, that list is no longer on the decode path (the call issues 2 descriptors), so #100 was re-scoped: find row h's cause and certify one DMA shape that can feed the GEMV at ≥ 37 GB/s while the vector unit works — the feed wall 1 now needs.
  3. The round trip — closed on 2026-09-22 (#88). It cost 401 µs per call in #88's own control run (22 calls per token). Most of that was not the arguments (464 bytes per call) but two things: (a) the activation and output buffers had grown to the prompt's size, 4 MiB each, and the FastRPC driver keeps a whole cached buffer consistent between ARM and DSP on every call — so every decode call paid for flushing 4 MiB although it used 8 KiB; (b) the ARM waited for the answer by polling (spinning on a flag) for only 100 µs, and a 1.4 ms call always outlived that and fell back to the slower interrupt wake-up. Upstream's size-class staging (a 64 KiB buffer for decode) and a 5 ms poll window, merged as PR #103, took the transport to 87.9 µs per call (−78 %): 245.8 µs of the cut is the staging, 67.6 µs the poll. Decode rose +30.9 / +41.4 / +42.9 %, text identical, prefill −0.9 % (inside the −5 % gate). On the GEMV path, now the default, #105 read 182–184 µs per call; whether the extra ≈ 95 µs belongs to that path is measured inside the next sitting (LEDGER ⑦).

How the work is organised

  • Decode first, NPU-only first. Order: measure (done, #77 and #94) → the three walls in the order the measurements dictate (wall 3 closed by #88; wall 1's GEMV is the default since PR #108 and #105 showed it is waiting on its weight feed; #100 now certifies a DMA feed into VTCM for it) → one FastRPC call per token with the whole layer stack resident on the DSP → prefill residency later. contract §3.1–3.2; LEDGER §2 budget row, §3
  • Every performance claim comes from a handoff: a document the user runs on the phone in one sitting, always as a full-model end-to-end run, always with the unchanged control binary first. Any S25 Ultra may be used; the handoff names no serial and the filled copy records the one used. Its binaries must be rebuildable from the named commits on any workstation (LEDGER rule 22). contract §4.2, §12 (2026-09-22); LEDGER rule 22
  • No Hexagon simulator: kernels are proven by host checks (scalar stand-ins, and since PR #107 the SDK's HVX emulation) and then by the device. contract §4.1, decisions log; PR #107 body
