1. Overview

This branch adds a Hexagon cDSP backend so that Qwen3 causal-LM inference can run on Qualcomm Hexagon's HVX vector units, driven from nntrainer on the host Android CPU over FastRPC. The goal is graph-level offload: the DSP receives the whole decoder-layer op sequence and keeps every large buffer persistently mapped, so decode costs one FastRPC round-trip per generated token rather than one round-trip per tensor op.

An earlier HexKL-based backend existed on this branch and was removed in commit 2c1b167b ("Wire enable-hexagon into the meson/ndk build, drop the HexKL backend") in favor of a self-built FastRPC skeleton with custom HVX kernels — giving full control over the wire format, buffer lifetime, and kernel implementations instead of depending on a third-party SDK layer.

The resulting stack works in three stages. On the host, a graph-lowering step turns a model's shape into a versioned "op-list" buffer (a fixed-layout header plus one descriptor per op) and a packed weight image. That op-list buffer and the model's tensors — weights, KV cache, activation scratch — cross the FastRPC boundary as shared, zero-copy rpcmem buffers. On the DSP side, a graph executor walks the op-list, validating it once and then dispatching each op's HVX kernel across a QuRT worker pool (one worker per HVX unit) per inference call.

See docs/backend_guide/HEXAGON.md for build and run instructions, the full architecture writeup, and measured results.

2. Architecture

End to end, a call flows in one direction and returns in one hop. On the host, graph lowering turns a model's shape into a versioned op-list plan (qwen3_lowering), which is serialized into an op-list v2 buffer placed in a shared rpcmem allocation. A single FastRPC invoke hands that buffer — plus the weights, KV cache, and activation-scratch buffers — to the cDSP, where the op-list executor validates it once and dispatches each op's HVX kernel across a QuRT worker pool. Weights are preloaded once, before the first token, as a packed DSP weight image that already includes the precomputed RoPE cos/sin table, so no weight or table data is repacked per call.

The op-list is a versioned flat buffer: a fixed 64-byte nntr_htp_oplist_header followed by n_ops fixed 64-byte nntr_htp_op_desc records (v2 adds these per-op descriptors on top of the v1 header prefix, commit a2800de7). Each op descriptor's tensor references — in0/in1/in2/out — are a struct nntr_htp_tensor_ref: a buf id selecting one of the five named buffers (WEIGHTS/KV/ACT/TOKENS/LOGITS) plus a 128-byte-aligned byte offset into it. No tensor data is embedded in or copied through the op-list itself; only this buffer-index-plus-offset pair crosses the FastRPC boundary, and it resolves against buffers that were already handed off once, at init(), as shared rpcmem allocations.

3. Milestones

M0 — FastRPC infrastructure

The backend started with the graph-level cDSP offload contract: nntr_htp.idl, the FastRPC interface where large buffers (weights/kv/act) cross once at init() as dma-buf fds for persistent HAP_mmap on the DSP, and forward() carries only token_ids/logits, one RPC per call — and nntr_htp_common.h, the plain-C op-list wire header (magic + ABI version) both the NDK and hexagon-clang toolchains compile. The DSP side got a dummy executor proving the plumbing (persistent mapping of the three dma-buf fds, ABI-mismatch rejection) and tools/hexagon/build_skel.sh cross-building the skel with hexagon-clang.

The host side added rpcmem_allocator (a move-only RAII dma-buf wrapper) and hexagon_runner, which owns one remote_handle64 session and requests an unsigned PD best-effort, the same path ggml-hexagon uses. An on-device round-trip test closed the loop, verifying host-written weights are visible through the persistent mapping: measured 168/258.5/598 us (min/median/max) over 32 forward calls on an 8 Elite device. M0 finished by wiring -Denable-hexagon into the meson/NDK build and dropping the legacy HexKL htp_backend, whose decode path measured net-harmful (~0.16 TPS).

M1 — HVX kernels

Before any kernel could run, M1 built the hexagon-sim test harness (v75 QuRT sim via runelf.pbn) under test/hexagon/sim/, extended the op-list wire format to v2 with 64-byte op descriptors and named buffer ids for the qwen3 graph, added a QuRT worker pool with per-op barrier semantics (correctly decoding qurt_hvx_get_units() as an encoding, not a raw count), and imported HVX exp/inverse and DMA-queue primitives from ggml-hexagon (MIT-licensed, with a NOTICE entry).

Seven kernels followed under nntrainer/tensor/hexagon/htp/ops/: W8A8 matmul with per-token dynamic int8 quantization and VTCM weight streaming double-buffered through the imported DMA queue; RMSNORM with a PER_HEAD mode for qwen3's QK-Norm; ROPE rotating q/k rows from a precomputed fp16 cos/sin table instead of computing trig on the DSP; ADD (using the normalized IEEE fp16 add rather than qf16, which lost precision on near-cancelling sums) and SILU_MUL; EMBED gather-dequant; a fused ATTN kernel combining KV-cache append with causal SDPA and GQA head-group sharing; and MATMUL_LOGITS emitting fp32 last-token logits directly. Each kernel shipped with a hexagon-sim test compared against a scalar C reference, verified PASS on hexagon-sim v75.

M2 — Op-list graph executor

htp_graph_init validates the wire op-list once, sizes the quantization and attention scratch from an op scan, and best-effort acquires VTCM with a DDR fallback. forward rejects the runtime arguments init cannot see — zero or over-chunk n_tokens, pos overflowing max_seq, a logits size mismatch — then dispatches the ops through the kind table with no per-op checks. A golden test hand-lowers a synthetic 2-layer, 35-op model and runs prefill then decode against a scalar reference executor that interprets the same op-list bytes. The executor is wired into the FastRPC entry point in executor.c, keeping the M1 dummy round-trip path working unmodified for the on-device test.

The backend guide was renamed from HEXAGON_HVX.md to HEXAGON.md and extended to cover the executor, the op kernels, the QuRT worker pool and VTCM, the op-list wire format v2, and the simulator golden tests, with a re-measured S25 Ultra RPC baseline (min 231 / median 255 / max 284 us over 32 calls).

M3 — Qwen3 graph lowering

A host-side compiler turns qwen3 dimensions into a complete v2 op-list execution plan. Applications/CausalLM/hexagon/qwen3_lowering.cpp lays out a 128-byte-aligned WEIGHTS cursor (embed, scales, RoPE table, fp16 norms, per-layer tensors), reusable ACT slots, and emits 1 + 16*n_layers + 2 op descriptors, with the tied embedding shared byte-for-byte between EMBED and MATMUL_LOGITS. The model recipe deliberately lives in the application layer so the hexagon backend in nntrainer/tensor/hexagon/host/graph_lowering.h stays model-agnostic; the runner only consumes the lowered result. test/hexagon/test_lowering.cpp checks the emitted plan structurally and smoke-tests real qwen3-0.6b dimensions: 451 ops and a 598,623,744-byte weight image by exact recompute.

pack_weights in nntrainer/tensor/hexagon/host/graph_lowering.cpp then fills that WEIGHTS image: int8 projection blobs and fp32 per-channel scale arrays are copied byte-for-byte at their reserved offsets, norm gammas are converted fp32 to fp16, and the RoPE table is generated in place — row p holds 64 fp16 cosines followed by 64 fp16 sines of p * theta^(-2i/128), the DSP-side counterpart the ROPE kernel from M1 reads at runtime. The backend guide gained a "Graph lowering and weight packing" section documenting the lowering API, the WEIGHTS image layout, and the op sequence, and recorded M3 as implemented with M4 (device end-to-end wiring) next.
