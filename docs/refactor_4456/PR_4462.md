<details><summary>[CausalLM] Pin MHACoreLayer's host attention against a plain reference</summary><br />

[CausalLM] Pin MHACoreLayer's host attention against a plain reference

MHACoreLayer has no test of its own. unittest_causallm_models runs whole
models, so a change inside the layer is seen only through end-to-end logits,
and only for the models and paths those fixtures happen to take. Moving the
layer's backend selection into ComputeOps (#4451) needs a step-by-step check
that the layer's output did not change.

unittest_mha_core runs the layer the way every CausalLM model does -- the
external KV cache mode, a prefill followed by decode steps -- and compares
each step's output with a reference written from the formula:
softmax(rope(Q) rope(K)^T / sqrt(head_dim) + mask) V. The reference rounds
K and V through fp16 as the cache stores them, so the two agree to 1e-4.

17 cases cover both host arms (per-row and use_gemm_attention), MHA and GQA,
chunked prefill, sliding window, no RoPE, softcap, the encoder
(non-causal) case, attention sinks, and the yarn and proportional RoPE
tables. A mutation of the default RoPE frequencies fails the 13 cases that
use them; disabling softcap on the per-row arm fails softcap_rowwise.

One case pins a gap instead of the formula: the host flash arm
(gemm_attention) never applies attn_logit_softcapping, while the per-row
arm and the OpenCL arms do. Gemma2 and Gemma4 set both softcap and
use_gemm_attention, so on the cpu engine their attention runs without
softcap. softcap_gemm_not_applied records today's output so this change
stays test-only; fixing the arm is a separate change that flips the case.

No production code changes.

[CausalLM] Keep unittest_mha_core's gemm cases on the arm they name

Review of #4462 found that the *_gemm cases reach the host flash arm only
on x86. min_prefill_thr() is 32 elsewhere and host_decode_prefers_per_row()
sends every decode step to the per-row arm, so with these 1-6 row steps an
ARM build ran every gemm case on the per-row arm: softcap_gemm_not_applied
failed there, and the other gemm cases re-tested their rowwise twins.

- Skip the gemm cases off x86, with the reason, mirroring the layer's own
  architecture gate. The per-row cases still run everywhere.
- Skip, naming the variable, when the process environment sets one of the
  variables the layer reads to choose its arm or KV-cache layout
  (NNTR_MIN_PREFILL, NNTR_MHA_GPU, NNTR_MHA_GPU_DECODE, NNTR_CUDA_ATTN,
  NNTR_KV_INT8, NNTR_KV_OHWI, NNTR_KV_WINDOW_RING). The layer latches most
  of them once per process, so the test cannot clear them.
- Add gemm_multi_tile and window_gemm_multi_tile, which set the flash
  tile (VJEPA_BQ / VJEPA_BK, read per call) to 2x4 and 2x2. The default
  256x512 tile never splits these short sequences, so the online-softmax
  rescale across key blocks and the window block skip were not run.
  Dropping the rescale now fails exactly these two cases; skipping one
  block too many fails window_gemm_multi_tile.
- Write the sink weight in its own dtype: FP16 on an Android fp16 build.
- Build the cases with named setters instead of 16 positional fields, and

- State the scope in the header: the tolerance is an absolute 1e-4; gemm
  cases are x86-only; batch 1, no ring, no int8 cache; the yarn and
  proportional tables follow the layer rather than Hugging Face.

<details><summary>[CausalLM] Own the flash tile environment in unittest_mha_core</summary><br />

[CausalLM] Own the flash tile environment in unittest_mha_core

gemm_attention reads VJEPA_BQ / VJEPA_BK (its flash tile) on every
call. unittest_mha_core set them only for the flashTile() cases, so:
- a shell that exported them ran the default-tile cases with another
  tile, and VJEPA_BQ=0 crashed the test binary with a division by zero
  (num_qb = (N_q + Bq - 1) / Bq);
- flashTile(bq, 0) exported VJEPA_BK=0, the same division by zero, and
  flashTile(0, bk) was silently ignored.

Since the variables are not latched, the test now owns them in every
case: it sets the case's tile, or unsets both for the layer's default,
and restores them afterwards. A case that gives only one tile size fails
with a message. ScopedEnv takes a null value to unset a variable.

The file header also says two things more precisely:
- The cases feed FP32 activations, so they pass in an enable-fp16 build
  too (checked on x86 and on aarch64 under qemu); what such a build does
  not cover is FP16 activations. The old wording read as if an fp16 build
  needed a looser tolerance for this file.
- A sliding window is tested on causal cases only: with a non-causal
  input the per-row arm ignores the window while the flash arm applies
  it, and the reference follows the per-row arm.

Checked: with VJEPA_BQ=0 VJEPA_BK=0 exported, the test crashed with
SIGFPE before and passes now; flashTile(2, 0) fails the case with the
message.

[CausalLM] Hold unittest_mha_core to fp16 precision on an Android fp16 build

On an Android fp16 build MHACoreLayer narrows FP32 activations to FP16
copies and runs its FP16 kernels (mha_core.cpp, ENABLE_FP16 &&

Hold the comparison to 1e-2 on that build, the fp16 tolerance the FP16

the layer computes in FP32. The header now says which build takes which.

cases skip as designed. x86 enable-fp16=false: 19/19, unchanged.

### Summary

- New `unittest_mha_core` (`Applications/CausalLM/layers/`, registered next to `unittest_kv_ring`) drives `causallm::MHACoreLayer` through `finalize()` and `incremental_forwarding()` in external-KV-cache mode. It checks every step's output against a plain attention reference that includes RoPE, GQA, causal and sliding-window masks, softcap and sinks, and rounds K/V through fp16 as the cache stores them.
- 19 cases: MHA, GQA, chunked prefill, sliding window, no RoPE, softcap, encoder (non-causal), attention sink, yarn and proportional RoPE, plus two flash cases with a small tile that span several query and key blocks.
- Which host arm runs:
  - The per-row cases (`use_gemm_attention=false`) run on every architecture.
  - The gemm cases reach the host flash arm only on x86, where it takes every step. Elsewhere they skip with the reason (review feedback).
  - The test also skips, naming the variable, when an environment variable that changes the layer's arm or KV layout is set.
  - The flash tile variables (`VJEPA_BQ` / `VJEPA_BK`) are not latched, so the test sets or unsets them itself in every case (review feedback).
- The test detects changes in the layer:
  - Changing the default RoPE frequencies in `mha_core.cpp` fails the 13 cases that use them; the no-RoPE, yarn and proportional cases still pass, as they should.
  - Disabling softcap on the per-row arm fails only `softcap_rowwise`.
  - Dropping the flash arm's online-softmax rescale fails only the two multi-tile cases.
  - Skipping one window key block too many fails `window_gemm_multi_tile`.
- Found while writing it, filed as #4461: the host flash arm (`gemm_attention`) ignores `attn_logit_softcapping`, which affects Gemma2/Gemma4 on the cpu engine. `softcap_gemm_not_applied` pins today's behaviour so this PR stays test-only; the fix for #4461 flips that one case.
- `unittest_mha_core` is added to the CausalLM cell's `required_tests` in `ubuntu_clean_meson_build.yml`, so the test cannot drop out of CI silently.
- Scope:
  - CI builds CausalLM tests only in the x86 `-Denable-fp16=false` cell.
  - Also checked locally: x86 `-Denable-fp16=true` 19/19; aarch64 (`-Darm-arch=armv8.2-a -Denable-fp16=true`) under qemu-user 10 passed, 9 gemm cases skipped as designed.
  - Run on a Galaxy S26 Ultra (SM8850, Android 16, NDK r30, `build_android.sh` CPU build, fp16): 10 per-row cases pass, 9 gemm cases skip. On that build the layer narrows FP32 activations to FP16 (`mha_core.cpp`, `ENABLE_FP16 && __ANDROID__`), so the per-row cases are held to 1e-2 there (8e-4 measured) and to 1e-4 everywhere else; see the fifth commit. The sixth adds the test to the CausalLM ndk-build harness so it can be built for a device.
  - Not run with OpenCL/CUDA. FP16 activations are not covered here (they come with #4464).
  - Batch 1, no KV ring, no int8 cache; a sliding window only on causal cases.
  - Device-vs-CPU comparisons come with the `ComputeOps` migration PRs (#4451).
