> 2. `MHACoreLayer`로 prefill(16토큰 한 번에)을 실행하고, 이어서 decode(1토큰씩)를 몇 번 실행합니다.
> 3. 같은 입력으로 **수식 그대로 짠 단순 attention**을 계산합니다. 약 20줄짜리 루프입니다.
>    ```
>    out = softmax(Q·Kᵀ / sqrt(d) + causal_mask) · V
>    ```
> 4. 2와 3의 결과가 허용 오차(fp32는 1e-5, fp16은 1e-2 정도) 안에서 같은지 검사합니다.
> 5. GQA, sliding window, RoPE 종류, kv_int8 같은 설정 조합마다 1~4를 반복합니다.
>
> ### 필요한 이유
> - 리팩토링 PR은 "동작이 바뀌지 않았다"를 증명해야 하는데, **지금은 이 레이어를 직접 검증하는 테스트가 없습니다.**

>
> ## 2. 원하시는 구조와 Phase 2의 관계
>
> **원하시는 구조가 Phase 2이고, 그 구조는 nntrainer에 이미 있습니다.** `mha_core`만 그 구조를 쓰지 않고 있는 상태입니다.
>
> ### 이미 이 구조를 쓰는 예: SwiGLU
> 레이어 코드는 백엔드를 전혀 모르고 메서드 하나만 부릅니다.
> ```cpp
> // nntrainer/layers/llm/swiglu_layer.cpp
> in1.getOps()->swiglu(in1, in2, out, rows, 0);
> ```
> `getOps()`가 무엇을 돌려주는지는 그 레이어에 지정된 context가 정합니다.
>
> | 레이어 engine | Context | `getOps()`가 돌려주는 객체 | `swiglu()` 실행 위치 |
> |---|---|---|---|
> | cpu | AppContext | `CpuComputeOps` | CPU 커널 |
> | gpu | ClContext (`cl_context.cpp:304`에서 등록) | `ClComputeOps` | OpenCL 커널 (`swiglu_cl_op`) |
> | cuda | CudaContext (`cuda_context.cpp:432`에서 등록) | `CudaComputeOps` | CUDA 커널 |
> | htp | HtpContext | `HtpComputeOps` | Hexagon NPU |
>
> 레이어 코드에는 `#ifdef`나 환경변수 분기가 없습니다. 백엔드별 코드는 각 `*ComputeOps` 클래스 안에만 있습니다.
>
> ### mha_core의 현재 방식
> 레이어 함수 하나 안에서 `#if ENABLE_OPENCL`, `#if ENABLE_CUDA`, `getenv("NNTR_MHA_GPU")` 같은 분기로 직접 백엔드를 고릅니다. context를 거치지 않습니다.
>
> ### Phase 2를 하면
> ```cpp
> // mha_core.cpp (목표)
> q.getOps()->rope(q, k, freqs, positions);
> q.getOps()->attention(q, k_cache, v_cache, out, params);
> ```
> 1. `ComputeOps`에 `rope()`, `attention()` 같은 메서드를 추가합니다. 지금은 없고, 문서 §10에도 빠져 있다고 적혀 있습니다.
> 2. `mha_core`는 위처럼 메서드만 호출하게 바꿉니다.
> 3. 레이어 안의 OpenCL 코드는 `ClComputeOps::attention()`으로, CUDA 코드는 `CudaComputeOps::attention()`으로 옮깁니다.
>
> ### 주의할 점 두 가지
> - **NPU는 HTP만 이 구조에 들어갑니다.** QNN은 그래프 전체를 벤더 바이너리에 한 번에 넘기는 방식이라 메서드 단위 선택을 거치지 않습니다(문서 §6, §9.3). 원하시는 구조에서 말하는 NPU는 `HtpComputeOps`입니다.
> - **`attention()`은 메서드를 정의하는 일이 가장 어렵습니다.** 백엔드마다 KV 캐시 메모리 배치가 다릅니다. OpenCL은 image mirror와 ring buffer를 씁니다. 그래서 `attention()`의 인자로 KV 캐시를 어떻게 넘길지를 먼저 설계해야 합니다. `rope()`는 비교적 단순해서 첫 대상으로 적합합니다.
>

>
> ## 왜 실패했나 (비유 없이)
>
> 안드로이드용 빌드에는 오래전부터 이런 코드가 있습니다. "안드로이드이고 fp16이 켜져 있으면, FP32로 들어온 입력을 FP16으로 바꿔서 계산해라." 폰에서 빠르게 돌리려는 의도적인 설계입니다.

>

>

[CausalLM] Pin MHACoreLayer's host attention against a plain reference

MHACoreLayer has no test of its own. unittest_causallm_models runs whole
models, so a change inside the layer is seen only through end-to-end logits,
and only for the models and paths those fixtures happen to take. Moving the
layer's backend selection into ComputeOps (#4451) needs a step-by-step check
that the layer's output did not change.

unittest_mha_core runs the layer the way every CausalLM model does -- the
external KV cache mode, a prefill followed by decode steps -- and compares
each step's output with a reference written from the formula:
softmax(rope(Q) rope(K)^T / sqrt(head_dim) + mask) V. The reference rounds
K and V through fp16 as the cache stores them, so the two agree to 1e-4.

17 cases cover both host arms (per-row and use_gemm_attention), MHA and GQA,
chunked prefill, sliding window, no RoPE, softcap, the encoder
(non-causal) case, attention sinks, and the yarn and proportional RoPE
tables. A mutation of the default RoPE frequencies fails the 13 cases that
use them; disabling softcap on the per-row arm fails softcap_rowwise.

One case pins a gap instead of the formula: the host flash arm
(gemm_attention) never applies attn_logit_softcapping, while the per-row
arm and the OpenCL arms do. Gemma2 and Gemma4 set both softcap and
use_gemm_attention, so on the cpu engine their attention runs without
softcap. softcap_gemm_not_applied records today's output so this change
stays test-only; fixing the arm is a separate change that flips the case.
