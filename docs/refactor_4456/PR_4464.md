<details><summary>[ComputeOps] Add a rotary_embedding whole-op</summary><br />

[ComputeOps] Add a rotary_embedding whole-op

RoPE has no ComputeOps entry, so the one layer that needs it,
causallm::MHACoreLayer, calls the CPU kernel directly and selects its
OpenCL and CUDA arms with preprocessor and environment branches inside the
layer. ARCHITECTURE_REFACTOR.md lists the missing virtual as what blocks
moving those arms behind the op table (#4451).

Add ComputeOps::rotary_embedding(in, out, head_dim, table, start_pos,
rotate). It rotates every head_dim-wide head of each row in the
rotate-half layout, with height index h at absolute position
start_pos + h, and writes FP32 (in place or not) or fp16 bits, which is
how a layer writes rotated keys straight into an fp16 KV cache. With
rotate false it only copies or converts, the value side of that write.

The table is passed as a RotaryTable: cos and sin as
[positions, head_dim / 2] rows behind stable pointers. That is the form
the device kernels already consume (rope_inplace_f16_cl's LUT, the CUDA
upload), and the CPU kernels read only the first half of each row, so one
layout serves every backend and a device table can cache its upload by
pointer.

CpuComputeOps implements it with compute_rotary_emb_value, row by row,
exactly as the layer's host loop did, plus a bounds check on the table
rows. CudaComputeOps inherits it, and the HTP table is the CPU table
itself. ClComputeOps delegates
to the CPU table for now: the device RoPE is still chosen inside the
layer, which settles the queue before it reaches the host path, so
nothing changes for the OpenCL engine until that arm moves here. The base
default throws, like every other whole-op.

FP32 input only. The FP16-input host kernel exists only in the ARM
backend, so taking it into the core table needs an arch guard; it comes
with the FP16 path of the layer, where it can be checked on ARM.

Tests in unittest_compute_ops_dispatch: dispatch through an attached
table against the rotate-half formula, the fp16-bits write with and
without rotation, and the table bounds check.

<details><summary>[CausalLM] Route MHACoreLayer's host FP32 RoPE through rotary_embedding</summary><br />

[CausalLM] Route MHACoreLayer's host FP32 RoPE through rotary_embedding

apply_rotary_emb_tensor_v2 called compute_rotary_emb_value itself for an
FP32 input, once per row, against a per-position vector of cos/sin rows.
Call in.getOps()->rotary_embedding() instead, so the host RoPE goes
through the tensor's op table like the layer's neighbours do. That is
the seam the device arms move behind next (#4451).

The FP32 table moves to the RotaryTable layout: [positions, head_dim / 2]
in one vector instead of a vector of head_dim-wide rows. The second half
of each old row repeated the first, and the kernels read only the first
half, so the values the kernels see are unchanged; the table is half the
size. The FP16 table and its users (the host FP16 path, the OpenCL and
CUDA arms) are untouched.

No behaviour change. unittest_mha_core, which pins the layer's host
output, passes unchanged; offsetting the position inside the new op makes
10 of its cases fail, so the layer does run through it. The OpenCL + FP16
configuration compiles with werror.

ARCHITECTURE_REFACTOR.md §4 and §10 now say rope has a virtual and which
part of the layer still bypasses it.

<details><summary>[cpu_backend] Add the fp16 rotary kernel to the x86 and fallback backends</summary><br />

[cpu_backend] Add the fp16 rotary kernel to the x86 and fallback backends

compute_rotary_emb_value(width, dim, half, _FP16 *inout, _FP16 *output,
cos, sin) is declared for every enable-fp16 build in cpu_backend.h, but
only the ARM backend defines it (NEON). Code outside an ARM build that
calls it therefore cannot link, so the one caller, MHACoreLayer's FP16
host RoPE, has to stay where only ARM compiles it.

Define it in the x86 and fallback backends too, forwarding to a new
__fallback_compute_rotary_emb_value: the same rotate-half pairing as the
NEON kernel, with the two products of each output taken in fp32 and
rounded once where NEON rounds each fp16 product. The ARM backend keeps
its NEON kernel.

<details><summary>[ComputeOps] Take FP16 input in rotary_embedding</summary><br />

[ComputeOps] Take FP16 input in rotary_embedding

rotary_embedding handled FP32 input only, because the FP16 kernel was
ARM-only; the previous commit makes it available in every enable-fp16
build.

RotaryTable gets cos_fp16 / sin_fp16: the same [positions, head_dim / 2]
layout as fp16 bits, stored as uint16_t so compute_ops.h stays free of
_FP16 and its layout does not depend on the build. CpuComputeOps rotates
an FP16 input into an FP16 output (in place or not) with that table,
row by row through compute_rotary_emb_value, exactly as MHACoreLayer's
FP16 host loop does today. An FP16 input always rotates: the copy-only
form exists for the FP32 value write, and no FP16 caller uses it. A
build without enable-fp16 rejects an FP16 input.

The op also rejects, with std::invalid_argument as its documentation
says, the arguments no kernel can take: a head_dim of 0 (every rotary
kernel's head loop would not advance), an odd head_dim or one that does
not divide the row width (the kernel would read past the row), and an
FP32 rotation without the fp32 table, as an FP16 one without the fp16
table.

unittest_compute_ops_dispatch:
- RotaryEmbeddingRotatesFp16Input: dispatch, the rotate-half formula,
  in-place equals out-of-place, and the copy-only rejection; enable-fp16
  builds only.
- RotaryEmbeddingRestartsPositionsPerBatch: every batch starts again at
  start_pos.
- RotaryEmbeddingRejectsBadHeadDimOrTable: the head_dim checks, through
  the copy-only form as well, which reads no table, so each condition is
  the only one that stops its case; and the missing fp32 table. Dropping
  the zero condition ends the test with a division by zero; dropping the
  odd one fails it.

[CausalLM] Route MHACoreLayer's host FP16 RoPE through rotary_embedding

The FP16 branch of apply_rotary_emb_tensor_v2 -- the host RoPE an
Android fp16 build runs -- still called compute_rotary_emb_value itself.
Call in.getOps()->rotary_embedding() instead, as the FP32 branch does,
so all of the layer's host RoPE goes through the op table.

It reads a [positions, head_dim / 2] fp16 table, the RotaryTable
layout, which precompute_freqs now keeps in rope_freq_cache
(cos_fp16_flat / sin_fp16_flat). The OpenCL RoPE already read a table of
that shape and values, built by ensure_rope_flat_lut into a second
cache, rope_flat_cache, keyed by (head_dim, theta, max_pos) only: two
layers differing in rope_scaling_type, scaling factor or partial rotary
factor would have shared the first layer's table. Drop rope_flat_cache:
ensure_rope_flat_lut now points rope_cos/sin_flat_cur at
rope_freq_cache's flat table and returns at once when they are already
set (setProperty clears them), so the host and the OpenCL RoPE read one
table. rope_freq_cache's key gains rope_partial_rotary_factor, which
_compute_proportional_parameters uses and the key lacked, so it holds
every RoPE parameter. The fp16 row table stays for the CUDA arm until it
moves behind the op.

No behaviour change for the models in tree:
- On ARM the op calls the same NEON kernel with the same rows and
  positions; the kernel reads only the first half of each row, which is
  what the flat table holds.
- The OpenCL RoPE reads the same bits as before. Each model has one RoPE
  configuration, except Gemma3 (sliding and global layers differ in
  theta) and Gemma4 (sliding and full layers differ in head_dim and
  theta), so no two configurations shared an old key, and no two differ
  only in the partial rotary factor.
- The position cap is unchanged (rope_lut_positions()); a position past
  it, which indexed past the row table (or a null row) before, is now
  rejected by the op.
The repeated call on the OpenCL hot path is now one pointer check
instead of a map lookup under the lock. The OpenCL + FP16 configuration
compiles with werror; the device path was not run.

through the virtual; the device arms do not yet.

### Summary

- Moves all of `MHACoreLayer`'s host RoPE behind `ComputeOps` (#4451): a `rotary_embedding` whole-op, which the layer's FP32 and FP16 host RoPE call through `in.getOps()`. The OpenCL and CUDA device RoPE arms are untouched and still chosen inside the layer; they move with the KV-cache write op, behind the same table.
- `RotaryTable` holds cos/sin as `[positions, head_dim / 2]` behind stable pointers. It carries an fp32 and an fp16 (as `uint16_t` bits) pair. This is the layout `rope_inplace_f16_cl` and the CUDA upload already use, and the half each CPU kernel reads, so one table type serves every backend.
- Per backend:
  - `CpuComputeOps` implements the op: FP32 in → FP32 / FP16 / UINT16 out, and FP16 in → FP16 out. It rejects a `head_dim` that is 0, odd or does not divide the row, and a missing table, with `std::invalid_argument`.
  - `CudaComputeOps` inherits it; the HTP table is the CPU table.
  - `ClComputeOps` delegates to the CPU table, as the layer did before.
  - The base default throws.
- The FP16 kernel `compute_rotary_emb_value(_FP16 ...)` was ARM-only. x86 and fallback versions are added, so the core table can call it in every enable-fp16 build. The layer's own x86 copy of it is removed, so the symbol is defined once, in libnntrainer.
- One flat fp16 RoPE table: the OpenCL RoPE and the host FP16 RoPE now read the same table in `rope_freq_cache`, keyed by every RoPE parameter (the partial rotary factor was missing from the key and is added). This replaces a second copy (`rope_flat_cache`) keyed by `(head_dim, theta, max_pos)` only. For the models in tree the OpenCL RoPE reads the same bits as before.
- Tests:
  - `unittest_compute_ops_dispatch`, 6 new cases: dispatch and the rotate-half formula; fp16-bits write with and without rotation; FP16 input; table bounds check; positions restarting per batch; rejection of a bad `head_dim` (with and without rotation) or a missing fp32 table.
  - `unittest_mha_core`, 3 FP16-activation cases (`fp16_rowwise`, `fp16_window_rowwise`, `fp16_gemm`, x86 only). These are the first test of the FP16 path an Android fp16 build runs.
  - CI now builds CausalLM in the `enable-fp16=true` Meson cell too, so those cases run there, and checks that the cell builds `unittest_mha_core` (`unittest_causallm_models` is built without enable-fp16 only).
- Mutations that the tests catch:
  - Offsetting the position in the FP32 branch fails 10 `unittest_mha_core` cases.
  - Swapping cos and sin in the FP16 branch fails exactly the 3 FP16 cases.
  - Dropping the zero or the odd condition of the `head_dim` check fails `RotaryEmbeddingRejectsBadHeadDimOrTable`.
