<details><summary>[CausalLM] Apply attn_logit_softcapping on the host flash attention arm</summary><br />

[CausalLM] Apply attn_logit_softcapping on the host flash attention arm

MHACoreLayer has two host attention arms. The per-row arm
(softmax_triangle) applies the Gemma2-style logit softcap,
score = cap * tanh(score / cap), before the softmax; the flash arm
(gemm_attention) went from the QK block straight to the mask and the
online softmax, and never applied it (#4461).

Gemma2 and Gemma4 set both attn_logit_softcapping and use_gemm_attention,
so on the cpu engine their attention ran without the softcap:
- on x86 the flash arm takes every step, prefill and decode;
- on ARM it takes prefill steps of 32 rows or more, while decode goes to
  the per-row arm, so a prefill and the decode after it used different
  formulas.

Apply the softcap to each score block right after the QK product, in
both score paths of the flash arm (FP32 scores, and the ARM FP16 scores
of an FP16 query). It goes before the causal and window mask: the mask
writes -inf, and tanh would turn that into -cap and let a masked key
back into the softmax. Models without a softcap are unchanged.

The CUDA arm inside gemm_attention is still handed a softcap of 0; its
comment no longer claims it matches this function, and it is left to a
separate change.

unittest_mha_core:
- softcap_gemm_not_applied, which pinned the gap, becomes softcap_gemm
  and expects the softcap like every other case.
- softcap_window_gemm combines it with a sliding window of 3, the
  configuration of Gemma2's sliding layers.
- softcap_gemm_multi_tile runs the softcap over 2 x 4 flash tiles.
- softcap_gemm_long_prefill uses a 40-row prefill, which takes the flash
  arm on ARM too, so it is the one gemm case that runs off x86. The skip
  for gemm cases off x86 now applies only when no step reaches 32 rows.
- That ARM flash step stores the softmax probabilities in fp16 and is
  about 5e-4 off the reference with or without softcap (4.5e-4 without,
  5.7e-4 with, under qemu), so it is held to 2e-3; every other step keeps
  1e-4. Without the fix the same step is 0.13 off.

On x86, removing the fix fails exactly the softcap gemm cases, and so
does applying the softcap after the masks instead of before them. On
aarch64 (qemu), removing it fails softcap_gemm_long_prefill.

Resolves #4461 for the host arm.

### Summary

- Fixes #4461. On the cpu engine, Gemma2 and Gemma4 ran attention without `attn_logit_softcapping`, because they set `use_gemm_attention` and the host flash arm (`gemm_attention`) never applied the softcap. The per-row arm and the OpenCL arms already did.
- Host flash arm:
  - The softcap is applied to each score block right after the QK product.
  - Both score paths are covered: FP32 scores, and the ARM FP16 scores of an FP16 query.
  - It is applied **before** the causal / window mask. Otherwise the mask's `-inf` would become `-cap` and masked keys would re-enter the softmax.
- CUDA arm: `cuda_attention_interleaved_fp16` was passed a softcap of `0.0f`. Every kernel behind it already applies the softcap when given one, so it now gets the layer's value, and its header comment says so. **The CUDA commit was not compiled or run** (no CUDA toolkit here). A run on a CUDA machine with Gemma2 or Gemma4 would be appreciated, e.g. prefill + decode with `NNTR_CUDA_ATTN` on vs. `=0`.
- Models without a softcap are unchanged on every arm.

  - `softcap_gemm_not_applied` becomes `softcap_gemm` and now expects the softcap.
