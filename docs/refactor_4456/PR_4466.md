[ComputeOps] Add a kv_cache_write whole-op

MHACoreLayer writes each step's keys and values into its KV cache
itself: it computes the cache row (pos, or pos modulo the ring size),
rotates K into it with rotary_embedding, and converts or copies V. The
device writes (OpenCL, CUDA) are chosen next to it with preprocessor and
environment branches. ARCHITECTURE_REFACTOR.md wants that choice behind
the op table (#4451); this adds the op the host write moves behind
first.

ComputeOps::kv_cache_write(k, v, kv, pos, rope) writes the step's rows
to cache rows [pos, pos + rows) -- modulo ring_cap on a ringed cache --
rotating K at its absolute positions when a RotaryTable is given and
converting both to the cache's fp16 element. The cache is described by a
KVCacheView: the batch's K and V planes, head_dim and the ring size. A
null plane is skipped: until the device writers and the OHWI scatter of
K move behind the op, the caller writes that half itself. The view gets
a layout and an element type when the OHWI and int8 writers move behind
the op; no caller would set them today.

CpuComputeOps implements the fp16 concat cache: K through
rotary_embedding, V through rotary_embedding's convert-only form for an
FP32 input (fp16 bits on every architecture) or a copy for an FP16 one.
It rejects rows past the cache end or across the ring seam.
CudaComputeOps inherits it, the HTP table is the CPU table, and
ClComputeOps delegates to it as it does for rotary_embedding. The base
default throws.

unittest_compute_ops_dispatch:
- KvCacheWriteDispatchesAndPlacesRows: dispatch, K rotated at its
  absolute positions, V in fp16 bits, other rows untouched.
- KvCacheWriteWrapsOnARing: rows land at pos % ring_cap while K still
  rotates by its absolute position; a step across the seam is rejected.
- KvCacheWriteSkipsNullPlaneAndRejects: a null plane is skipped; a write
  past the last row is rejected.
Shifting the row by one, ignoring the ring, or rotating K by its ring row
fails these tests.

### Summary

**What this PR does**
- Adds `ComputeOps::kv_cache_write(k, v, kv, pos, rope)`, the op that writes one step's K and V rows into a KV cache. It is the second whole-op of #4451 after `rotary_embedding`.
  - Cache row: `pos`, or `pos % ring_cap` on a ringed cache. A step that would run past the last row or across the ring seam is rejected.
  - K is rotated at its absolute position when a `RotaryTable` is given. V is converted to fp16 bits (FP32 input) or copied (FP16 input).
  - `KVCacheView` holds one batch's K and V planes, `head_dim` and `ring_cap`. A null plane is skipped, so the parts that do not go through the op yet (OpenCL / CUDA device writes, the OHWI scatter of K) keep writing their half themselves.
  - `CpuComputeOps` implements it on top of `rotary_embedding`. `ClComputeOps` delegates to it, `CudaComputeOps` inherits it, HTP uses the CPU table, the base throws.
- `MHACoreLayer`'s three host cache writes (RoPE path, no-RoPE path, attention-sink overload) now call it through a `write_kv_cache()` helper. The device arms, the OHWI scatter and int8 stay in the layer for now.
- Behaviour: unchanged on x86 and in enable-fp16 builds. One fix on ARM without enable-fp16: the no-RoPE path wrote an FP32 step into the UINT16 cache with `copyData`, an integer cast there (`__fallback_copy_fp32_u16`). It now gets a real fp16 conversion, like x86 and the RoPE path.

**Design of the remaining `mha_core.cpp` steps (for review)**

This PR is the first step of a plan to take every backend choice out of `MHACoreLayer::one_batch_incremental_forwarding`. Comments on the plan are welcome here.

- Goal: the function comes down to Q RoPE, `kv_cache_write`, then `attention`, all through `tensor.getOps()`, with no `#if ENABLE_OPENCL` / `ENABLE_CUDA` and no `getenv` in the layer. The context's op table picks the backend; the op picks the kernel inside it.
- What has to move:
  - KV writes: host concat (this PR), host K-OHWI scatter (`NNTR_KV_OHWI`), host int8 (internal-cache mode only), OpenCL concat, OpenCL OHWI image mirror, CUDA (including the `d_pos` slot form for graph replay).
  - Attention arms: host per-row, host flash (`gemm_attention`), CUDA, and four OpenCL families (two_conv, K-OHWI direct, image mirror, flash). They differ in which of window / softcap / sink / ring / int8 they support.
  - Device state the layer keeps only because it is the one place that knows every arm: the OHWI mirrors and image views, their watermarks, queue-drain flags, GPU_CLMEM residency handles.
- Planned interface additions, each added in the step that first uses it (none is in this PR, where no caller would set them):
  - `KVCacheView` gains a layout (`Concat` / `KOhwi`) and an element type (`F16` / `Int8` with per-(row, head) scales). The layout is fixed when the cache is allocated instead of being re-derived from the environment on every call.
  - A backend-owned `KVCacheState` in the view holds the OpenCL mirrors and watermarks, so they leave the layer. The image mirror is backend state, not a layout: the cache tensor itself stays concat.
  - `attention(q, kv, out, AttentionParams{num_heads_q, q_pos, kv_len, causal, window, scale, softcap, sink})`. The sink becomes a parameter, so the two `one_batch_incremental_forwarding` overloads become one.
- Rules for every backend:
  1. Apply the whole formula or decline: an arm that cannot apply a parameter (softcap, sink, window, ring, int8) must not run; the op falls through to its next arm and finally to the CPU op. #4461 (softcap silently dropped) was this kind of gap.
  2. The op owns coherence: a device op that falls back to the host settles its own queue first. The layer never drains.
  3. Kernel choice is internal to the op. At first the op reads the same env vars the layer reads now (a move, not a redesign); ARCHITECTURE_REFACTOR §10 later turns them into ExecPlan cells.
  4. Positions are host values; the CUDA op keeps publishing `d_pos` for a replayable step.
- Stays in the layer: properties and `finalize`, the RoPE table, `skip_prefill`, building `KVCacheView` from the bound cache tensors, the batch loop.
- Order (each step keeps `unittest_mha_core` passing):

  | Step | Contents | Verifiable without a device? |

  | 6a | **This PR**: `kv_cache_write`, CPU, concat / fp16 | yes (x86, aarch64 qemu) |
  | 6b | Fix #4461 so the attention move is a pure move: #4465 | yes |
  | 6c | `attention`, CPU: move the host per-row and flash arms into `cpu_backend`; the sink overload goes away | yes; large, but a move |
  | 6d | CPU K-OHWI and int8 behind the ops (or retire int8, see Q4) | yes |
  | 7a | OpenCL concat write and attention in `ClComputeOps`, CPU fallback inside the op | build only; needs a device run |
  | 7b | OpenCL image mirror plus `KVCacheState` | needs Adreno |

  Before 7a, `unittest_mha_core` needs a device variant that runs the same cases on the `gpu` engine against the same reference (the #4452 harness).
- Open questions for maintainers:
  - **Q1.** 6c moves the host attention kernels from `Applications/CausalLM` into core `cpu_backend`, because `CpuComputeOps` is core. Proposal: core. Is that acceptable?
  - **Q2.** `KVCacheState` ownership. Proposal: a `shared_ptr` in the view, held by the layer and created by the op on first use. Alternative: a map in `ClContext` keyed by the cache memory, which has lifetime issues when caches are rebound.
  - **Q3.** Gemma4 KV-shared layers bind another layer's cache but each builds its own OHWI mirror. With the state attached to the cache they could share one; that is a behaviour and memory change, to be decided separately after 7b.
  - **Q4.** int8 KV works only in internal-cache (3-input) mode, which no CausalLM model uses. Keep it and implement it in 6d, or retire it?
  - **Q5.** The FP32-activation narrowing to FP16 host copies in `forwarding` / `incremental_forwarding`: move it into the CPU op too, or leave it in the layer until step 9?
