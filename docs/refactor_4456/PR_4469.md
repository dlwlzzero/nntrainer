[cpu_backend] Add the fp16 per-row attention kernels to the x86 and fallback backends

cpu_backend.h declares the all-FP16 kernels of the per-row attention
for every enable-fp16 build: compute_kcaches and
compute_fp16vcache_transposed with _FP16 query, cache and output, and
the _FP16 specializations of softmax_row_inplace / softmax_row. Only
the ARM backend defines them (NEON). MHACoreLayer's FP16 per-row
attention calls them, so mha_core.cpp carried its own x86 definitions
of all four, in namespace nntrainer, inside the layer library.

That keeps the per-row attention tied to the layer: core code cannot
call these kernels on x86, which is what moving the attention behind a
ComputeOps whole-op (#4451) needs next. It also leaves the definitions
where the backend's are expected, as the rotary kernel was until the
previous series dropped its copy.

Move them into libnntrainer, as __fallback_compute_kcaches,
__fallback_compute_fp16vcache_transposed and
__fallback_softmax_row_inplace (fp16 overloads), with the x86 and
fallback backends forwarding to them; softmax_row forwards to the
in-place one, as the layer's copy did. The code is the layer's,
unchanged: fp32 accumulation, no tiling. The ARM backend keeps its NEON
kernels, and mha_core.cpp drops its copies.

Checked on x86 with enable-fp16: libmha_core_layer.so no longer exports
any of the four, libnntrainer.so does, and unittest_mha_core passes
unchanged, its three FP16-activation cases included, so the layer runs
the moved kernels with the same results. The enable-fp16=false build
and the aarch64 build are unaffected (the layer's block was x86 and
enable-fp16 only).

<details><summary>[ComputeOps] Move MHACoreLayer's host per-row attention behind an attention whole-op</summary><br />

[ComputeOps] Move MHACoreLayer's host per-row attention behind an attention whole-op

MHACoreLayer computes its host per-row attention itself, in three
member functions: compute_kcaches (scores row by row), softmax_triangle
(the softmax over each row's visible keys, with the logit softcap, and
an overload with the attention sink) and compute_fp16vcache_transposed
(the weighted sum of the values), plus their FP32-cache and int8-cache
kernels. ARCHITECTURE_REFACTOR.md wants attention behind the op table
(#4451); CpuComputeOps is in core and core cannot call into
Applications/, so the code moves to core.

ComputeOps::attention(q, kv, out, AttentionOpParams) computes
softmax(softcap(Q K^T / sqrt(d)) + mask [+ sink]) V over keys
[0, kv_len) of a KVCacheView, with GQA, a causal mask, a sliding window
and an optional per-head sink. KVCacheView gains the per-(row, head)
fp16 scales of an int8 cache; int8 is read from the planes' UINT8
dtype, as the layer allocates them.

CpuComputeOps implements it in the new cpu_attention.cpp with the
layer's code, moved as it was: the three member functions keep their
bodies and become members of a RowwiseAttention struct whose fields are
the layer state they read (is_causal, local_window_size,
attn_logit_softcapping, kv_int8, the int8 scale pointers), and the
FP32-cache and int8 kernels move with them. The only edit to the moved
bodies is a size_t cast on the query row offset, so the product cannot
overflow before it is widened. The op allocates the score buffer the
layer allocated, and rejects a ringed cache, which the per-row arm cannot
read (the layer still asserts that before the call), mismatched shapes,
a kv_len other than q_pos + rows or past the cache rows, and dtypes no
arm reads: an FP32 query over an int8 cache, an FP16 query over an FP32
one, K and V of different dtypes, an output of another dtype than the
query. CudaComputeOps
inherits it, the HTP table is the CPU table, ClComputeOps delegates to
it, the base default throws.

MHACoreLayer calls it through a new attend_rowwise() helper from both
places that ran the per-row arm: the host attention of
one_batch_incremental_forwarding and the attention-sink overload, which
passes its sink. The layer's choice between its host arms, the flash arm
(gemm_attention) and the device arms are unchanged and stay in the
layer.

MHACoreLayer::calc_windowed_attn_index has no caller left and goes; the
op keeps its own copy.

The per-row arm applies the window only to causal rows when it sizes and
normalises the scores, but its K and V kernels apply it to every row, so
a non-causal input with a window shorter than kv_len gets an unspecified
result. That is how the layer behaved; the op documents it as
unsupported rather than change it in a move.

No behaviour change. The only difference is the score buffer of the
sink overload's decode step: it was `to` rows and is now the
min(to, window) rows the kernels write, the size the other call site
already used.

unittest_compute_ops_dispatch, each against a plain fp32 reference
computed from the values the tensors hold:
- AttentionDispatchesAndMatchesTheFormula: dispatch and the formula on
  two query rows, two query heads over one KV head, a window of 2 and a
  softcap; a ringed cache and a wrong kv_len are rejected.
- AttentionFp32QueryPaths: an FP32 query over an FP32 cache and over

### Summary

- **Q1 of #4466 (where the host attention kernels live): core.** `CpuComputeOps` is in core and core cannot call into `Applications/`, so the code moves to `nntrainer/tensor/cpu_backend/`.
- **Commit 1:** the all-FP16 per-row kernels (`compute_kcaches`, `compute_fp16vcache_transposed`, and the `_FP16` `softmax_row[_inplace]`) were defined for x86 inside `mha_core.cpp`, in namespace `nntrainer`. They move into libnntrainer as `__fallback_*`, with the x86 and fallback backends forwarding to them. The code is unchanged, and the ARM backend keeps its NEON kernels. `libmha_core_layer.so` no longer exports them.
- **Commit 2:** new whole-op `ComputeOps::attention(q, KVCacheView, out, AttentionOpParams)`, following the same pattern as `rotary_embedding` and `kv_cache_write`.
  - `CpuComputeOps` implements it in `cpu_attention.cpp`, `ClComputeOps` delegates to it, `CudaComputeOps` inherits it, HTP uses the CPU table, and the base throws.
  - The layer's per-row arm moves **as it was**. The three member functions keep their bodies and become members of a `RowwiseAttention` struct whose fields mirror the layer state they read. The FP32-cache and int8 kernels move with them.
  - `KVCacheView` gains the int8 scale pointers. int8 is detected from the planes' UINT8 dtype, which is how the layer allocates them.
  - `MHACoreLayer` calls the op through `attend_rowwise()` from both places that ran the arm: the main host path and the attention-sink overload.
  - About 700 lines leave `mha_core.cpp`.
- **Checks on the new op:** `attention()` also rejects a `kv_len` past the cache rows and dtypes no arm reads. Those are an FP32 query over an int8 cache, an FP16 query over an FP32 one, K and V of different dtypes, and an output of another dtype than the query. Every call the layer makes passes these checks.
- **Behaviour:** unchanged. The only difference is the score buffer of the sink overload's decode step, which is now sized to the rows the kernels write.
- **Known pre-existing gap, documented and not changed:** with non-causal rows and a window shorter than `kv_len`, the per-row arm's K/V kernels apply the window but its softmax does not, so the result is unspecified. The op's doc says so. Fixing it is a behaviour change for a separate PR. Gemma3/4 can configure non-causal attention with a sliding window.
- **Still in the layer:** the host flash arm (`gemm_attention`), the choice between the two host arms, and every OpenCL/CUDA arm. These are 6c-2 and steps 7–9.
