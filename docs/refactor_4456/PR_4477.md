[ComputeOps] Move MHACoreLayer's host flash attention arm and the host arm choice into the op

Step 6c-2 of the plan in #4466. After 6c-1 (#4469) the layer's host per-row
arm ran behind ComputeOps::attention, but the host flash arm
(gemm_attention, 600 lines), the choice between the two host arms and the
CUDA arm that gemm_attention carried were still inside mha_core.cpp.

- AttentionOpParams gains `flash`: the flash-class arms may run (the
  layer's use_gemm_attention). Which arm runs is the backend's choice.
- CpuComputeOps::attention gets the flash arm as it was, as a
  FlashAttention struct whose fields keep the layer's names (the x86 AVX2
  fused fp16-bits GEMM comes with it), and the choice: flash when allowed,
  over an fp16-bits or int8 cache, without a sink, from flash_min_rows()
  rows (NNTR_MIN_PREFILL; x86 every step, ARM 32 rows or any with
  NNTR_MHA_GPU), and not for a decode row where the per-row arm is faster
  (ARM). These are the layer's min_prefill_thr() and
  host_decode_prefers_per_row(), read from the same environment.
- CudaComputeOps::attention is the CUDA arm (cuda_attention_interleaved_fp16)
  as it was, then the host arms: before falling to them it refuses a
  device-only pool with the layer's old message and settles the stream
  (drain_if_async), which the layer did only on its per-row path.
- The layer keeps the OpenCL arms and calls the op after them, through
  attend(); its two host tails become one. The two host-path guards go
  with that: the op refuses a ringed cache (the message now carries the
  hint) and the CUDA op the residency.
- The layer's exp copy (vjepa_expq_f32) is neon_mathfun's exp_ps, the
  same cephes sequence. The ARM fp16 kernels are now behind ENABLE_FP16,
  since libnntrainer also builds without it on ARM; there, and on other
  architectures, the generic arms widen the key / value tile to fp32 and
  run the fp32 GEMM instead of the former uncompilable sgemm call on
  fp16 bits.

Behaviour: unchanged on the cpu engine and the CUDA engine. Two paths
differ: a decode step a device arm declined now takes the per-row arm on
ARM (it fell to the host flash arm, measured 2.5-5x slower there), and
the flash arm's NNTR_MHA_ATTN_TIMER bucket for the CUDA arm is gone
(diagnostic). The x86 and ARM-fp16 kernels are the same code.

About 830 lines leave mha_core.cpp.

### Summary

- **What moves.** `MHACoreLayer::gemm_attention` (the host flash arm, with its x86 AVX2 fused GEMM and the ARM NEON fp16 forms) becomes `FlashAttention::run` in `cpu_attention.cpp`, next to the per-row arm of #4469; the arm choice (`flash_min_rows()`, `decode_prefers_per_row()`) is `CpuComputeOps::attention`'s. The CUDA arm the same function carried becomes `CudaComputeOps::attention`, which falls to the host arms the way the layer did (device-only pool refused, stream settled). The layer's `attend()` passes `AttentionOpParams::flash = use_gemm_attention` and no longer knows which host arm runs.
- **New op-level tests** (`unittest_compute_ops_dispatch`): `AttentionFlashArm` and `AttentionFlashArmFp16Query` run 40-row steps through the flash arm (ARM takes it from 32 rows) on 8 x 8 tiles with a softcap, a window, non-causal rows, a chunk after a prefill, a decode row, and an int8 cache, and check that a sink or an FP32 cache falls back to the per-row arm. The query amplitude of the existing attention cases is raised so a dropped softcap or window mask fails the tolerance.
- **Known gaps kept:** non-causal rows with a window are still unspecified on the per-row arm and masked on the flash arm (documented since #4469); the OpenCL arms, the device KV writes, OHWI and int8 writes stay in the layer (steps 6d, 7, 8).
