[ComputeOps] Write MHACoreLayer's K-OHWI and int8 KV caches through kv_cache_write

Step 6d of the plan in #4466. After #4466 the host concat write of the
KV cache went through kv_cache_write, but two host writes stayed in the
layer: the per-head K-OHWI scatter (NNTR_KV_OHWI, §3.8 of the paper) and
the int8 quantization of the internal cache (NNTR_KV_INT8, §3.7).

- KVCacheView gains the K plane's layout (KVCacheLayout::Concat / KOhwi)
  and its int8 element: UINT8 planes with the fp16 scale planes, whose
  pointers kv_cache_write now writes and attention reads (they were const).
- CpuComputeOps::kv_cache_write writes a KOhwi key plane per head (the
  step rotated and converted into concat order first, then scattered at
  each head's stride) and an int8 plane by quantizing each (row, head) of
  the fp16 step, K rotated first, with the scale amax / 127 into the same
  row of the scale plane. The scatter, gather and quantizer move from
  mha_core.cpp as they were into cpu_backend/kv_cache_layout.h, which both
  CPU ops include. An FP32 step is converted to fp16 bits first, so the
  int8 and KOhwi writes no longer need an FP16 step.
- CpuComputeOps::attention gathers a KOhwi key plane into concat rows
  [0, kv_len) before either host arm, as the layer did.
- The layer fixes kv_layout in finalize (NNTR_KV_OHWI on an fp16-bits
  cache that is not int8 and not on a KV window ring) instead of deriving it from the environment and the
  step's dtype on every write: the former write condition also asked for
  an FP16 step, which an FP32-activation x86 run never has, while the read
  did not, so NNTR_KV_OHWI on such a run wrote concat and read OHWI. The
  three write sites pass the layout and, for int8, the scale planes through
  write_kv_cache(); the int8 branch keeps its Q RoPE and the per-batch
  scale pointers for the read path. The host read-side gather stays in the
  layer for the OpenCL two_conv arm, which reads concat and takes a host
  copy; it goes with that arm in step 7a. It reads fp16 bits, so the
  UINT16 internal cache of a build without enable-fp16 takes KOhwi end to
  end (the gather threw there). A ringed layer keeps concat: the gather
  copies cache_to rows at the linear per-head stride into a plane only
  min(cache_to, Wcap) rows tall. The OpenCL OHWI gates (the device RoPE
  exclusion and the OHWI-direct arm) follow kv_layout too, instead of
  the NNTR_KV_OHWI latch. NNTR_KV_INT8 without enable-fp16 stops at
  finalize with its own message, as it stopped at the first step before.

Behaviour: unchanged on the paths models take (concat, fp16). The int8
write no longer rotates key_step in place (the op rotates into the cache;
nothing read key_step after). NNTR_KV_OHWI with FP32 activations on x86
now writes and reads the same layout. NNTR_KV_OHWI on a ringed layer is
concat (it overflowed the read); on a build without enable-fp16 the
internal cache is KOhwi and works (ohwi_internal_cache_rowwise runs
there).

### Summary

- **What moves.** The two host KV writes the layer still did itself: the per-head K-OHWI scatter (`NNTR_KV_OHWI`) and the int8 quantization of the internal cache (`NNTR_KV_INT8`, kept per the Q4 decision). `KVCacheView` gains the K plane's layout (`KVCacheLayout::Concat` / `KOhwi`) and its int8 element (UINT8 planes with writable fp16 scale pointers); `CpuComputeOps::kv_cache_write` writes both, `CpuComputeOps::attention` gathers a `KOhwi` plane before its arms. The scatter, gather and quantizer move as they were into `cpu_backend/kv_cache_layout.h`.
- **Layer.** `kv_layout` is fixed in `finalize()` (NNTR_KV_OHWI on an fp16 cache that is not int8), the three write sites pass it through `write_kv_cache()`, the int8 branch passes the scale planes and keeps only its Q RoPE and the read-side scale pointers. The read-side gather stays for the OpenCL two_conv arm (it reads concat and takes a host copy) until that arm moves in 7a; the op receives the gathered Concat plane.
- **Behaviour.** Unchanged on the paths models take. Two differences on the env-gated paths: the int8 write no longer rotates `key_step` in place (nothing read it afterwards), and `NNTR_KV_OHWI` with FP32 activations on x86 now writes and reads the same layout (the former write condition also asked for an FP16 step while the read did not).
- **Tests.** `unittest_mha_core`: internal-cache mode, int8 (per-row and the 40-row flash prefill, FP16 activations) and K-OHWI (with and without RoPE, per-row and flash) cases, which set `NNTR_KV_INT8` / `NNTR_KV_OHWI` themselves. `unittest_compute_ops_dispatch`: the KOhwi scatter placement, attention over a KOhwi plane equal to the concat one bit for bit, the int8 write's values and scales against the formula (and the refusal without scales), and an int8 write read back by attention.
