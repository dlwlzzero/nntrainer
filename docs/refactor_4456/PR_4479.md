[ComputeOps] Run MHACoreLayer's OpenCL flash and two_conv attention arms from ClComputeOps

Step 7a of the plan in #4466, first slice. After 6c (#4469, #4477) the
layer's host attention arms and the CUDA arm run behind
ComputeOps::attention, but the layer still chose and ran its OpenCL
attention arms itself: the flash kernels (a decode form and a prefill
form, over shared virtual memory) and the two_conv kernels, inside the
device block of one_batch_incremental_forwarding, next to the image arm.

ClComputeOps::attention runs those arms now, in the layer's order and
under the layer's gates: NNTR_MHA_GPU on, NNTR_MIN_PREFILL rows (default
1) or a single row the layer admits, no sink, FP16 q / out / cache, a
concat K plane; the flash kernels over SVM planes, two_conv over SVM or
host copies. Then the host arms. The decode permission the layer took
from its gpu_decode_attn property (or NNTR_MHA_GPU_DECODE) travels as
AttentionOpParams::device_decode. A step the gates admit but no kernel
takes goes to the host arms after one queue drain, so they read what the
device wrote into the planes; a step the gates decline goes at once (the
layer drained only when it knew of staged writes). The two_conv kernels
apply neither the softcap nor the window, as before; the flash kernels
do, and they map the logical range onto a KV window ring
(NNTR_KV_WINDOW_RING), whose planes the layer hands over only as tall as
the ring. The arm checks the planes against those rows
(KVCacheView::rows_read), not against kv_len, so a ringed layer past the
window keeps its device arm; the host arms cannot read a ring.

The layer's block keeps the int8 GPU arm, the image arm (with its OHWI
mirror, step 7b) and the clmem staging modes; its flash / two_conv
section goes, and a step the image arm does not take falls through to
attend(). The flash arm's NNTR_MHA_ATTN_TIMER bucket goes with it
(diagnostic), as the CUDA arm's did in #4477.

A planner cl_mem output (the GPU_CLMEM residency) is landed in that
buffer by the op, because only the op knows which arm wrote it:
after a device arm, the GPU-to-GPU copy the layer ran after its flash /
two_conv arms (with NNTR_NO_GPU_OBRIDGE, a drained host upload, as
there); after a host arm, the host upload the layer's host tail ran. The
layer's tail upload goes: run after a device arm, it would read the
kernel-written SVM shadow as a host pointer, which a coarse-grained SVM
does not make coherent. The sink variant's exit upload skips the step
the op already landed.

An FP32-activation layer stages FP16 copies of Q, K, V and O in shared
virtual memory (attention_fp32_on_device) and runs the step on them.
Those planes were bare Tensors, whose op table is the CPU one, so with
the arms behind the op they would have taken the host flash arm instead
of the device kernels; they now carry the source tensors' context data
and reach ClComputeOps like the layer's own FP16 planes. That path maps
the planes for the host (settle_act_stage_for_host) before the op call,
where it mapped them before the host tail only; on the fine-grained SVM
the Adreno path uses the map is the drain it always was.

Behaviour: unchanged on the cpu and CUDA engines (the op is OpenCL
only). On the gpu engine the same kernels run on the same inputs, with
two differences: the drain before a host fallback runs whenever a kernel
refused a step the gates admitted (the layer's ran only for staged
writes), and
the staged planes of an FP32-activation step are mapped before the
device arm runs rather than after it (above).

### Summary

- **What moves.** The two OpenCL attention arms the layer ran itself over its concat FP16 cache, the flash kernels (`flash_decode_f16_cl`, `flash_attention_prefill_f16_cl`, over SVM planes) and the two_conv kernels (`two_conv_attention_prefill_f16_cl`, its image2d variant under `NNTR_MHA_GPU_IMG`), become `ClComputeOps::attention`'s (`cl_device_attention_arm` in `cl_compute_ops.cpp`), in the layer's order and under the layer's gates, followed by the host arms after one queue drain. The layer's device block keeps the int8 GPU arm, the Adreno image arm with its OHWI mirror (7b) and the clmem staging modes; its flash / two_conv section is gone, and a step the image arm does not take falls through to `attend()`.
- **One new parameter.** `AttentionOpParams::device_decode`: the layer's `gpu_decode_attn` property or `NNTR_MHA_GPU_DECODE`, which let a single-row step take a device arm; the host arms ignore it.
- **Behaviour.** Unchanged on the cpu and CUDA engines. On the gpu engine the same kernels run on the same inputs; the one difference is that the drain before a host fallback is unconditional (the layer drained only when it knew of staged writes). The two_conv kernels still apply neither the softcap nor the window, as before; the flash kernels do. The flash arm's `NNTR_MHA_ATTN_TIMER` bucket is gone (diagnostic), as the CUDA arm's was in #4477.
- **Second commit: the device RoPE and concat KV write.** `ClComputeOps::rotary_embedding` rotates an FP16 SVM activation in place with `rope_inplace_f16_cl` and `ClComputeOps::kv_cache_write` rotates K straight into its concat cache rows and copies V there (`gpu_copy_f16_cl`), both drained, as the layer's plain SVM path did, under its gates; the no-RoPE, OHWI and int8 writes stay the host's. The layer leaves that plain form to the ops and keeps its image-arm, staged and cl_mem forms (7b). On Adreno the gpu context turns the image arm on by default (`cl_context.cpp`), so there a gemm layer still takes the layer's image form; a per-row layer, and every layer with `NNTR_KV_IMG_ATTN=0` or on a device without the image arm, takes the ops'.
- **No new test in this PR.** The test that covers these arms is the device mode of `unittest_mha_core` (#4473's first commit), which this branch does not carry; it was applied on top locally for the device run below. No CI cell builds `-Denable-opencl=true` together with `-Denable-transformer=true`, so CI compiles neither the op's arm nor the layer's block.
