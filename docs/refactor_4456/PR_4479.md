[ComputeOps] Run MHACoreLayer's OpenCL flash and two_conv attention arms from ClComputeOps

Step 7a of the plan in #4466, first slice. After 6c (#4469, #4477) the
layer's host attention arms and the CUDA arm run behind
ComputeOps::attention, but the layer still chose and ran its OpenCL
attention arms itself: the flash kernels (a decode form and a prefill
form, over shared virtual memory) and the two_conv kernels, inside the
device block of one_batch_incremental_forwarding, next to the image arm.

ClComputeOps::attention runs those arms now, in the layer's order and
under the layer's gates: NNTR_MHA_GPU on, NNTR_MIN_PREFILL rows (default
1) or a single row the layer admits, no sink, FP16 q / out / cache, a
concat K plane; the flash kernels over SVM planes, two_conv over SVM or
host copies. Then the host arms. The decode permission the layer took
from its gpu_decode_attn property (or NNTR_MHA_GPU_DECODE) travels as
AttentionOpParams::device_decode. A step no device arm takes goes to the
host arms after one queue drain, so they read what the device wrote into
the planes; the layer drained only when it knew of staged writes. The
two_conv kernels apply neither the softcap nor the window, as before;
the flash kernels do.

The layer's block keeps the int8 GPU arm, the image arm (with its OHWI
mirror, step 7b) and the clmem staging modes; its flash / two_conv
section goes, and a step the image arm does not take falls through to
attend(). The flash arm's NNTR_MHA_ATTN_TIMER bucket goes with it
(diagnostic), as the CUDA arm's did in #4477.

An FP32-activation layer stages FP16 copies of Q, K, V and O in shared
virtual memory (attention_fp32_on_device) and runs the step on them.
Those planes were bare Tensors, whose op table is the CPU one, so with
the arms behind the op they would have taken the host flash arm instead
of the device kernels; they now carry the source tensors' context data
and reach ClComputeOps like the layer's own FP16 planes. That path maps
the planes for the host (settle_act_stage_for_host) before the op call,
where it mapped them before the host tail only; on the fine-grained SVM
the Adreno path uses the map is the drain it always was.

Behaviour: unchanged on the cpu and CUDA engines (the op is OpenCL
only). On the gpu engine the same kernels run on the same inputs, with
two differences: the drain before a host fallback is unconditional, and
the staged planes of an FP32-activation step are mapped before the
device arm runs rather than after it (above).
